## 1. 핵심 수치 (인용용)

측정 조건: 상품 10만 · 찜 50만 · 키워드 2만 건, 앱 컨테이너 CPU 2·메모리 1.5GB, k6 고정 도착률, 워밍업 1분 + 측정 3분, 동일 조건 3회 반복.

| 항목 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 찜 목록 요청당 SQL 실행 수 (페이지 10 / 50 / 100건) | 13 / 53 / 103건 | 2 / 2 / 2건 |
| 찜 목록 응답 p50 (페이지 10 / 50 / 100건) | 8.4 / 16.0 / 25.6 ms | 5.3 / 5.7 / 6.1 ms |

| 상품 등록 요청당 SQL 실행 수 | 24건 | 14건 |
| 상품 등록 SQL 시간 | 133 ms | 5.1 ms |
| 상품 등록 p50 (키워드 210건 데이터) | 44.5 ms | 35.4 ms |

## 2. 전체 버전 (약 1,500자)

**"측정할 수 없으면 고칠 수 없다고 생각해, 개선보다 측정 환경을 먼저 만들었습니다."**

팀 프로젝트에서 제가 구현한 상품 조회·찜·키워드 알림 기능을 개인 저장소로 이어받아 성능 관점에서 다시 다뤘습니다. 먼저 Docker로 DB·애플리케이션·Prometheus·Grafana·k6를 묶고 앱 컨테이너에 CPU 2개·메모리 1.5GB를 고정했습니다. 상품 10만·찜 50만·키워드 2만 건을 시드를 고정해 재현 가능하게 적재하고, 요청마다 실행된 SQL 수를 응답 헤더로 확인할 수 있게 계측기를 붙였습니다. 비교의 전제가 되는 조건을 먼저 통제한 것입니다.

이 환경에서 세 가지 문제를 찾았습니다.

첫째, 찜 목록 조회의 쿼리 수가 반환 항목 수에 비례했습니다. 페이지 크기 10·50·100에서 요청당 SQL이 13·53·103건이었습니다. 원인을 따라가 보니 단순한 N+1이 아니라, 메인 쿼리가 채팅방을 조인한 채 찜 기준으로 그룹핑하고 있어 집계값이 틀렸고 그걸 항목마다 재조회로 보정하는 구조였습니다. 그래서 쿼리 수를 줄이는 대신 집계를 한 번에 올바르게 구하는 방향으로, 상품 기준 상관 서브쿼리로 바꿨습니다. 결과는 페이지 크기와 무관하게 2건으로 고정됐고, 응답 p50도 페이지 크기 100건 기준 25.6ms에서 6.1ms가 됐습니다. 개선 전에는 페이지 크기를 10배로 늘리면 응답 시간이 3배가 됐는데, 개선 후에는 5.3ms에서 6.1ms로 거의 평평합니다.

둘째, 상품 등록마다 전체 키워드를 메모리로 읽고 있었습니다. 리포지토리 메서드에 조건절이 없었고 캠퍼스·작성자·제목 조건을 전부 자바 스트림에서 걸렀습니다. 알림 대상이 0명이어도 키워드 2만 건을 매번 엔티티로 만들었습니다. 조건을 쿼리로 내리자 같은 데이터에서 등록 p50이 379ms에서 39.5ms가 됐습니다. 다만 DB collation이 대소문자를 구분하지 않아 알림 대상이 넓어질 수 있었기 때문에, DB 결과가 기존 조건의 상위 집합이라는 점을 이용해 대소문자 검사만 애플리케이션에 남겨 결과 집합을 그대로 유지했습니다.

셋째, 알림 전송이 요청 스레드와 쓰기 트랜잭션을 잡고 있었습니다. SDK의 `sendAsync`를 쓰면서 `.get()`으로 결과를 기다리고 있었고, 수신자 수만큼 순차로 반복했습니다. 전송을 커밋 이후 전용 executor에서 실행하도록 옮기고, 토큰 조회를 한 번의 `in` 조회로, 전송을 배치 호출로 합쳤습니다. 수신자 10명·지연 50ms 조건에서 등록 응답 p50이 876ms에서 16ms가 됐습니다.

가장 신경 쓴 부분은 **개선을 증명하는 방식**이었습니다. 응답이 빨라진 대신 작업이 뒤로 밀린 것이라면 개선이 아니므로, 측정이 끝난 시점에 생성된 상품 수와 전송 완료 수가 정확히 일치하는지, 큐 거절이 0인지를 함께 확인했습니다. 그 과정에서 제가 붙인 executor 지표가 값을 못 읽는 버그도 발견했습니다. 스레드풀을 직접 초기화한 뒤 지표를 연결했는데 스프링이 빈을 초기화하며 새 풀을 만들어, 지표가 버려진 객체를 보고 있었습니다.

남은 과제도 측정으로 확인해 뒀습니다. 상품 검색과 관리자 목록에는 같은 조인 구조가 남아 있어, 관리자 목록은 상품 10만 건에서 단건 요청이 0.5초이고 초당 10건을 보내면 처리량이 1건 아래로 떨어지며 타임아웃이 발생합니다. 이번 개선 대상이 아니었고 실제로 전후 수치가 거의 같아서, 바꾼 부분만 좋아졌다는 대조 근거로도 쓰였습니다. 다음 작업으로 정리할 계획입니다.

## 3. 1,000자 버전

**"개선보다 측정 환경을 먼저 만들었습니다."**

팀 프로젝트에서 제가 구현한 상품·찜·키워드 알림 기능을 개인 저장소로 이어받아 성능 관점에서 다시 작업했습니다. Docker로 DB·앱·모니터링을 묶고 앱 자원을 CPU 2개로 고정한 뒤, 상품 10만·찜 50만·키워드 2만 건을 재현 가능하게 적재하고 요청별 SQL 실행 수를 응답 헤더로 확인할 수 있게 만들었습니다.

측정으로 세 가지를 찾았습니다. 찜 목록은 요청당 SQL이 페이지 크기 10·50·100에서 13·53·103건으로 항목 수에 비례했습니다. 단순 N+1이 아니라 잘못된 집계를 항목별 재조회로 보정하는 구조였기 때문에, 상품 기준 상관 서브쿼리로 집계를 한 번에 구하도록 바꿔 2건으로 고정했고, 페이지 크기 100건 기준 응답 p50이 25.6ms에서 6.1ms가 됐습니다.

상품 등록은 매번 전체 키워드를 메모리로 읽고 자바에서 걸렀습니다. 조건을 쿼리로 내려 등록 p50을 379ms에서 39.5ms로 줄였고, DB collation 때문에 대소문자 판정이 달라지는 부분은 애플리케이션 필터를 남겨 결과 집합을 동일하게 유지했습니다.

알림 전송은 `sendAsync().get()`으로 요청 스레드와 트랜잭션을 잡고 있었습니다. 커밋 이후 전용 executor로 옮기고 토큰 조회와 전송을 각각 한 번으로 합쳐, 수신자 10명 기준 등록 응답 p50을 876ms에서 16ms로 줄였습니다.

가장 신경 쓴 것은 개선을 증명하는 방식입니다. 응답만 빨라지고 작업이 밀린 것이 아님을 확인하려고, 측정 종료 시점에 생성된 상품 수와 전송 완료 수가 일치하는지, 큐 거절이 0인지를 함께 검증했습니다. 상품 검색과 관리자 목록에 같은 문제가 남아 있다는 것도 측정으로 확인해 다음 과제로 정리했습니다.

팀 프로젝트에서 제가 맡았던 기능을 개인 저장소로 이어받아, Docker로 자원을 고정한 로컬 측정 환경과 상품 10만·찜 50만 건 규모의 재현 가능한 데이터를 만들었습니다. 요청별 SQL 실행 수를 확인할 수 있게 계측기도 붙였습니다.

## 6. 면접 1분 답변 스크립트

> "성능 개선 경험을 말해보세요"

팀 프로젝트에서 제가 만들었던 기능을 개인적으로 다시 다듬은 경험이 있습니다.

개선보다 측정을 먼저 했습니다. Docker로 DB와 앱, 모니터링을 묶고 앱 컨테이너 자원을 고정한 뒤, 상품 10만 건 규모 데이터를 재현 가능하게 적재했습니다. 요청마다 SQL이 몇 번 나가는지 헤더로 볼 수 있게도 만들었습니다.

그 상태에서 세 가지가 나왔습니다. 찜 목록은 페이지 크기를 10에서 100으로 늘리면 SQL이 13건에서 103건으로 늘었고, 상품 등록은 키워드 2만 건을 매번 전부 읽고 있었고, 알림 전송은 요청 스레드에서 외부 호출을 기다리고 있었습니다.

각각 집계 쿼리 재작성, 조건을 DB로 이동, 커밋 이후 비동기 전송으로 고쳤습니다. 찜 목록 SQL은 페이지 크기와 무관하게 2건이 되면서 응답도 25.6ms에서 6.1ms로 줄었고, 상품 등록 응답은 876ms에서 16ms가 됐습니다.

제일 신경 쓴 건 숫자를 정직하게 만드는 부분이었습니다. 비동기로 옮기면 응답은 당연히 빨라지니까, 전송이 실제로 다 끝났는지를 따로 확인했습니다. 생성된 상품 수와 전송 완료 수가 일치하는지, 큐에 남은 작업과 거절이 0인지를 같이 봤습니다.

## 7. 항목별 What · Why · How

### P1 · 찜 목록 집계 쿼리

- **What**: 찜 목록 조회가 반환 항목마다 추가 쿼리를 실행하던 구조를 상품 기준 집계 서브쿼리로 바꿨다.
- **Why**: 페이지 크기 10·50·100에서 요청당 SQL이 13·53·103건으로 정확히 항목당 1건씩 늘었다. 쿼리 하나하나는 짧아도 그동안 커넥션을 잡고 있으므로, 동시 요청이 늘면 커넥션 풀 대기로 나타난다. 원인을 보니 메인 쿼리가 채팅방을 조인한 채 찜 단위로 그룹핑해 집계값이 상품의 찜 수가 아니었고, 항목별 재조회는 그 값을 덮어쓰기 위한 보정이었다.
- **How**: 집계를 상품 기준 상관 서브쿼리로 옮기고 조인·그룹핑을 제거했다. 목록에 필요한 것이 연관 엔티티가 아니라 개수였고, 컬렉션 fetch join은 페이징과 함께 쓰면 메모리 페이징이 되기 때문에 선택하지 않았다. 결과 동일성은 기존 리포지토리 테스트(찜 수·채팅 수·isLiked 단언)가 그대로 통과하는 것으로 확인했고, "페이지 크기와 무관하게 쿼리 수가 같다"를 새 테스트로 고정했다.

### P2 · 키워드 매칭 조건을 DB로

- **What**: 전체 키워드를 읽어 자바에서 네 번 거르던 로직을 단일 쿼리 조건으로 옮겼다.
- **Why**: 상품 등록마다 키워드 20,010건을 엔티티로 만들었다. 알림 대상이 0명이어도 비용은 동일하고, 사용자가 늘수록 커지는 성질의 비용이 쓰기 경로 한복판에 있었다. 키워드 210건 데이터와 20,010건 데이터에서 등록 p50이 44.5ms와 379.1ms로 8.5배 차이 나는 것으로 확인했다. 두 조건의 SQL 실행 수는 24건으로 동일했다. 즉 실행 횟수가 아니라 한 쿼리가 읽는 행 수가 원인이었다.
- **How**: 캠퍼스·작성자·제목 조건을 JPQL `where`로 이동했다. 다만 DB collation이 대소문자를 구분하지 않아 그대로 두면 알림 대상이 늘어난다. 성능 작업이 동작 변경을 동반하면 안 된다고 판단해, DB 결과가 기존 조건의 상위 집합이라는 점을 근거로 대소문자 일치 검사만 애플리케이션에 남겼다. 개선 후 210건과 20,010건 데이터의 등록 p50은 35.4ms와 39.5ms로 거의 같아졌다.

### P3 · 알림 전송 비동기화

- **What**: 등록 트랜잭션 안에서 수신자마다 결과를 기다리던 전송을, 커밋 이후 전용 executor의 배치 전송으로 바꿨다.
- **Why**: `sendAsync(message).get()`은 이름과 달리 호출 스레드를 블로킹한다. 응답 시간이 외부 서비스 지연에 직접 묶이고, 그동안 DB 커넥션과 쓰기 트랜잭션이 열려 있다. 또 전송이 커밋 전에 일어나므로 롤백되면 없는 상품의 알림이 나간다. 모의 지연 200ms·수신자 10명 조건에서 등록 응답 p50이 2,445ms였다.
- **How**: 등록 시점에는 이벤트만 발행하고 `@TransactionalEventListener(AFTER_COMMIT)` + `@Async`로 커밋 이후 전용 스레드에서 전송한다. 커밋 후에는 영속성 컨텍스트가 닫히므로 이벤트에는 엔티티 대신 필요한 값만 담았다. 수신자별 토큰 조회는 `in` 절 한 번으로, 전송은 SDK의 배치 호출 한 번으로 합쳤다. 큐는 유한하게 두고 거절을 카운터로 세어, 한계를 메모리 문제가 아니라 관측 가능한 신호로 만들었다.

## 8. 검증에 대해 말할 거리

이 부분이 다른 지원자와 갈리는 지점이므로 반드시 준비한다.

1. **결과 동일성**: 쿼리를 바꾼 뒤에도 기존 리포지토리 테스트의 찜 수·채팅 수 단언이 그대로 통과했다. 새로 만든 테스트가 아니라 원래 있던 테스트다.
2. **작업이 밀리지 않았음**: 측정 종료 시점에 생성된 상품 242건과 디스패치 완료 242건이 일치했고, 메시지 2,420건이 모두 성공했다. executor 큐 잔량 0, 활성 스레드 0, 거절 0건이었다. 응답이 빨라진 만큼 일이 뒤로 밀린 게 아니라는 근거다.
3. **보수적인 측정 조건**: 모의 전송 지연을 배치 1회가 아니라 메시지 1건마다 적용했다. 실제 Firebase는 배치를 1회 호출로 처리하므로, 개선 폭을 과장하지 않는 쪽을 선택했다.
4. **도구 자체의 오류를 잡은 경험**: k6 threshold에 "목표 요청률 미달 0건"을 걸어두어 정상 실행이 실패 처리되던 문제, 그리고 스레드풀을 직접 초기화한 탓에 executor 지표가 버려진 객체를 보던 문제를 각각 발견해 고쳤다.
5. **한계 명시**: 단일 로컬 장비에서 DB·앱·부하 도구가 함께 돌아간다. 절대 수치를 운영 성능으로 일반화하지 않고, 같은 조건의 상대 비교로만 사용한다.

## 9. 남은 과제 (약점이 아니라 로드맵으로)

- 상품 검색과 관리자 목록에 P1과 동일한 조인 구조가 남아 있다. 관리자 목록은 상품 10만 건에서 단건 요청 약 0.5초, 10 req/s에서 실제 처리량 0.8 req/s에 타임아웃이 발생한다. 상품 검색도 30 req/s에서 무너진다.
- 알림 재시도와 outbox는 중복 방지 설계가 함께 필요해 이번 범위에서 제외했다.
- 인덱스는 실행 계획을 근거로 다음 단계에서 판단한다. 근거 없이 추가하면 쓰기 비용만 늘어난다.
