# 04. 성능을 어떻게 측정했는가

개선보다 먼저 한 일이 측정 환경을 만든 것이다. "느린 것 같아서 고쳤다"와 "이 조건에서 이 수치였고 이렇게 바뀌었다"는 다른 이야기다. 이 문서는 그 방법을 정리한다.

## 1. 왜 로컬에 측정 환경부터 만들었나

개선 전후를 비교하려면 **같은 조건**이 필요하다. 같은 데이터, 같은 자원 제한, 같은 부하, 같은 계측. 이게 보장되지 않으면 숫자가 달라져도 원인을 코드 변경이라고 말할 수 없다.

그래서 Docker Compose로 MariaDB·Redis·애플리케이션·Prometheus·Grafana·k6를 묶고, 애플리케이션 컨테이너에 CPU 2개·메모리 1.5GB·JVM 힙 1GB 제한을 고정했다. 자원이 고정되어야 "처리량 한계"라는 말이 의미를 가진다.

## 2. 데이터를 만드는 것도 설계다

| 프로필 | 사용자 | 상품 | 찜 | 키워드 |
| --- | ---: | ---: | ---: | ---: |
| smoke | 100 | 1,000 | 5,000 | 200 |
| small | 1,000 | 10,000 | 50,000 | 2,000 |
| medium | 10,000 | 100,000 | 500,000 | 20,000 |
| large | 100,000 | 1,000,000 | 5,000,000 | 200,000 |

지킨 규칙들:

- **난수 시드 고정**: 같은 명령이면 같은 데이터가 나온다. 비교의 전제다.
- **JDBC 배치 적재**: 수십만 건을 JPA `saveAll`로 넣으면 느리고 메모리를 먹는다. 청크 1,000건 단위로 커밋했다.
- **manifest 기록**: 실제 적재 건수, 분포, 시드, 적재 시간, DB 크기, 코드 버전을 JSON으로 남긴다. 측정 폴더마다 이 파일을 복사해서 "이 수치는 이 데이터에서 나왔다"를 붙여둔다.
- **적재 후 검증**: 목표 건수와 실제 건수 비교, 찜 중복 0건 확인. 데이터가 틀리면 측정이 전부 무의미하다.
- **API 우회 사실 명시**: seed는 서비스 로직을 거치지 않는다. 그래서 "상품 등록 성능"은 seed가 아니라 API 시나리오로 따로 측정했다.

## 3. 두 종류의 측정을 섞지 않는다

### (1) 쿼리 수 — 격리 실행

요청 스레드가 실행한 JDBC 문장 수를 응답 헤더로 내려주는 필터를 로컬 프로필에 붙였다(datasource-proxy + ThreadLocal 카운터).

```
X-Local-SQL-Count: 103
X-Local-SQL-Ms: 15
```

이건 **부하와 분리해서** 측정한다. 동시 요청이 섞이면 스레드별 카운터가 의미를 잃고, 전역 통계는 요청 단위로 환산할 수 없다. 그래서 요청 전후로 카운터를 초기화하고, 쿼리 수 비교는 단건 요청으로 확인했다.

### (2) 지연·처리량 — k6 부하

```js
scenarios: { load: { executor: 'constant-arrival-rate', rate, timeUnit: '1s',
  duration: '3m', preAllocatedVUs: ..., maxVUs: 200 } }
```

**고정 도착률(constant-arrival-rate)** 을 쓴 이유가 중요하다. VU(가상 사용자) 기반은 "응답이 빨라지면 더 많이 보내는" 구조라, 서버가 느려지면 부하도 같이 줄어든다. 그러면 서버가 느려진 게 지표에 제대로 안 나타난다. 고정 도착률은 **서버 상태와 무관하게 일정하게 보내고**, 서버가 못 따라오면 그 사실이 `dropped_iterations`(시작조차 못 한 작업)로 드러난다.

실제로 상품 검색 30 req/s 측정에서 목표 30인데 실제 16.8만 달성했고, 미시작 1,066건이 기록됐다. 이 숫자가 없으면 "p95가 13초"라는 값만 보고 원인을 오해하기 쉽다.

## 4. 측정 규칙 — 숫자를 정직하게 만드는 장치들

- **워밍업 1분 + 측정 3분**: JIT 컴파일, 커넥션 풀 생성, DB 캐시 예열 전 구간을 결과에 넣지 않는다.
- **같은 조건 3회 반복**: 1회 값은 노이즈일 수 있다. 실제로 재시작 직후인 1회차가 2·3회차보다 눈에 띄게 느렸다.
- **반복별 p95를 평균하지 않는다**: 백분위수는 평균이 안 된다. 각 실행의 원본 summary를 그대로 싣는다.
- **실행 조건을 함께 저장**: 커밋 해시, 작업 트리 dirty 여부, 컨테이너 이미지·CPU/메모리 제한, JVM 옵션, 모의 지연값, Docker 자원, seed manifest, 측정 전후 Prometheus 스냅샷.
- **실패한 실행도 남긴다**: 중단된 실행의 로그를 지우지 않는다. 성공한 요청만 모아 요약하면 붕괴를 못 본다.
- **단일 장비 한계를 명시**: DB·앱·부하 도구·모니터링이 같은 PC에서 돈다. 이 수치는 운영 환경 최대 성능이 아니다.

## 5. 측정 도구도 틀릴 수 있다

k6 threshold에 `dropped_iterations: ['count==0']`을 걸어뒀더니, 오류율 0%·체크 100%인 정상 실행이 목표 요청률을 몇 번 놓쳤다는 이유로 통째로 실패 처리됐다. 워밍업에서 실패하면 본 측정이 아예 시작되지 않았다.

여기서 배운 것: **기록해야 할 지표와 중단해야 할 조건은 다르다.** 미시작 작업은 "결과"이고, 서버 오류율 5% 초과는 "중단 사유"다. 둘을 같은 threshold로 묶으면 측정 자체가 사라진다.

그래서 `dropped_iterations`는 기록만 하도록 바꾸고, 워밍업 실패는 본 측정을 막지 않도록 고쳤다.

## 6. 병목을 어떻게 지목했나

상품 검색 측정에서 나온 숫자:

- 요청당 SQL **3건** — 쿼리 개수는 적다
- 그 3건의 DB 시간 평균 **69ms** — 응답 시간의 거의 전부
- 10 req/s에서는 p95 89ms로 안정, 30 req/s에서 붕괴

여기서 "쿼리 수가 적으니 문제 없다"는 결론은 틀렸다. **쿼리 개수와 쿼리 비용은 다른 축**이다. 이 경우는 개수(N+1)가 아니라 단일 쿼리의 구조(조인으로 중간 행을 부풀리고 그룹핑) 문제였다.

반대로 찜 목록은 쿼리 **개수**가 문제였다(13/53/103건). 같은 "느리다"라도 원인 축이 다르고, 고치는 방법도 다르다. 측정 지표를 둘 다 갖고 있었기 때문에 구분할 수 있었다.

## 7. 면접에서 나올 수 있는 질문

**Q. 성능 개선을 했다고 하는데 어떻게 검증했나요?**
개선 전에 먼저 측정 환경을 만들었습니다. 데이터 규모를 고정하고, 컨테이너 자원을 제한하고, 워밍업 1분 + 측정 3분을 3회 반복하는 조건을 정해두고 baseline을 확보했습니다. 개선 후에는 같은 seed manifest와 같은 부하 조건으로 다시 측정해서 비교했습니다.

**Q. 왜 고정 도착률을 썼나요?**
VU 기반은 서버가 느려지면 부하도 같이 줄어들어서 성능 저하가 지표에 덜 나타납니다. 고정 도착률은 일정하게 보내고, 서버가 못 받으면 미시작 작업 수로 드러납니다. 실제로 검색 API에서 목표 30 req/s 중 16.8만 달성하고 1,066건이 미시작으로 기록됐습니다.

**Q. 로컬 단일 장비 측정인데 의미가 있나요?**
절대 수치를 운영 성능으로 주장할 수는 없습니다. 다만 같은 장비·같은 데이터·같은 부하에서 코드만 바꿔 비교했기 때문에 **상대 비교**는 유효하다고 봅니다. 그리고 쿼리 실행 수처럼 장비와 무관한 지표는 그 자체로 구조 개선의 증거입니다.

**Q. 측정에서 가장 신경 쓴 부분은요?**
숫자를 좋아 보이게 만들지 않는 것입니다. 성공한 요청만으로 요약하지 않고, 중단된 실행과 미시작 작업을 결과에 남겼습니다. 모의 전송 지연도 개선 후에 배치로 한 번에 줄일 수 있었지만, 비교가 유리해지는 걸 피하려고 메시지당 지연을 그대로 유지해서 보수적으로 측정했습니다.
