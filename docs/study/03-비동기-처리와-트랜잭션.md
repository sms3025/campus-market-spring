# 03. 비동기 처리와 트랜잭션 경계

이 문서는 상품 등록 시 FCM 알림 전송을 요청 스레드에서 떼어낸 작업을 기준으로 정리한다. 코드는 `FcmNotificationService`, `FcmService`, `KeywordNotificationListener`, `AsyncConfig`이다.

## 1. 개선 전에 무슨 일이 있었나

```java
// ItemService.itemRegister — 클래스에 @Transactional이 걸려 있다
Item savedItem = itemRepository.save(newItem);
List<Keyword> sendingKeywords = keywordService.findKeywordsWithSameItemCampusAndTitle(savedItem);
notificationHistoryService.saveNotificationHistory(sendingKeywords, savedItem);
fcmService.sendFcmMessageWithKeywords(sendingKeywords, savedItem);   // ← 여기
```

```java
// FcmService — 수신자마다 토큰을 조회하고, 토큰마다 전송
for (Keyword k : sendingKeywords) {
    List<String> tokens = userFcmTokenRepository.findFcmTokenByUser_UserId(k.getUser().getUserId());
    for (String token : tokens) fcmNotificationService.sendNotification(...);
}
```

```java
// FcmNotificationService — 이름은 Async지만 결과를 기다린다
FirebaseMessaging.getInstance().sendAsync(message).get();
```

`sendAsync(...)`는 `ApiFuture`를 돌려준다. 여기에 `.get()`을 붙이면 **그 Future가 끝날 때까지 호출 스레드가 멈춘다.** 메서드 이름에 Async가 있다고 비동기가 아니다. 이걸 테스트로 증명해뒀다(`FcmBaselineTest.waitsForSdkFutureCompletion`): 완료되지 않은 Future를 물려주면 호출이 반환되지 않는다.

그래서 상품 등록 API 한 건의 응답 시간은

```
DB 작업 시간 + (수신자 수 × 토큰 수 × Firebase 왕복 시간)
```

이 되고, 그동안 **쓰기 트랜잭션과 DB 커넥션이 계속 열려 있다.**

측정값(수신자 10명, 모의 지연 50ms): p50 876ms, 요청당 SQL 24건.

## 2. 세 가지 문제로 분해하기

이 하나의 코드에 서로 다른 성격의 문제가 겹쳐 있다. 면접에서는 이걸 나눠서 말하는 게 중요하다.

1. **응답 시간 문제**: 사용자는 알림 전송이 끝날 때까지 기다릴 이유가 없다. 상품은 이미 저장됐다.
2. **자원 점유 문제**: 외부 서비스 왕복 동안 DB 커넥션과 트랜잭션을 잡고 있다. 커넥션 풀이 10개인데 등록 요청 10개가 동시에 오면 나머지는 전부 대기한다. 외부 서비스가 느려지면 DB가 멀쩡해도 서비스가 멈춘다.
3. **정합성 문제**: 전송이 커밋 **전에** 일어난다. 이후 트랜잭션이 롤백되면 존재하지 않는 상품의 알림이 이미 나가 있다.

## 3. 어떻게 고쳤나 — 순서가 중요하다

### (1) 트랜잭션 커밋 이후로 옮긴다

```java
// ItemService
eventPublisher.publishEvent(KeywordNotificationEvent.of(savedItem, sendingKeywords));
```

```java
@Async(AsyncConfig.FCM_EXECUTOR)
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onKeywordNotification(KeywordNotificationEvent event) { ... }
```

`@TransactionalEventListener(AFTER_COMMIT)`은 트랜잭션이 실제로 커밋된 뒤에만 리스너를 실행한다. 롤백되면 실행되지 않는다. 3번 문제가 여기서 해결된다.

`@Async`를 같이 붙이면 커밋 후 실행이 **호출 스레드가 아니라 지정한 executor에서** 일어난다. 1번과 2번 문제가 여기서 해결된다.

### (2) 이벤트에 엔티티를 담지 않는다

```java
public record KeywordNotificationEvent(Long itemId, String itemTitle, List<Target> targets) {
    public record Target(Long userId, String keywordName) { }
}
```

커밋 이후에는 영속성 컨텍스트가 닫혀 있다. 엔티티를 그대로 넘기면 지연 로딩 프록시를 건드리는 순간 `LazyInitializationException`이 난다. 그래서 트랜잭션 안에서 필요한 값만 복사해 이벤트로 넘긴다.

### (3) 전송 자체의 N+1도 없앤다

```java
List<Long> userIds = event.targets().stream().map(Target::userId).distinct().toList();
Map<Long, List<String>> tokensByUser = userFcmTokenRepository.findFcmTokensByUserIds(userIds)
    .stream().collect(groupingBy(UserFcmTokenDto::userId, mapping(UserFcmTokenDto::fcmToken, toList())));
```

수신자마다 토큰을 조회하던 것을 `in` 절 한 번으로 바꿨다. 비동기로 옮겼다고 해서 비효율이 사라지는 게 아니다. **비동기는 비용을 옮기는 것이지 없애는 게 아니다.** 옮긴 다음에도 줄여야 한다.

### (4) 배치 전송

```java
BatchResponse batchResponse = FirebaseMessaging.getInstance().sendEach(messages);
for (int i = 0; i < batchResponse.getResponses().size(); i++) {
    SendResponse r = batchResponse.getResponses().get(i);
    if (!r.isSuccessful() && r.getException() != null) handle(r.getException(), messages.get(i).getTargetToken());
}
```

Firebase Admin SDK 9.2.0의 `sendEach(List<Message>)`는 최대 500건을 한 번의 호출로 보낸다. 수신자 수만큼의 직렬 왕복이 1회로 줄어든다. 개별 실패는 `BatchResponse`의 인덱스별 결과로 확인해서, 기존의 토큰 정리(UNREGISTERED·INVALID_ARGUMENT면 토큰 삭제) 로직을 그대로 유지했다.

## 4. 스레드풀을 "그냥 만들지" 않는다

```java
executor.setCorePoolSize(2);
executor.setMaxPoolSize(4);
executor.setQueueCapacity(500);
executor.setThreadNamePrefix("fcm-");
executor.setRejectedExecutionHandler((task, pool) -> { rejected.increment(); log.warn(...); });
executor.setWaitForTasksToCompleteOnShutdown(true);
executor.setAwaitTerminationSeconds(20);
```

각 설정에 이유가 있어야 한다.

- **전용 executor**: 기본 `SimpleAsyncTaskExecutor`는 요청마다 스레드를 새로 만든다(풀이 아니다). 공용 executor를 쓰면 알림이 다른 비동기 작업을 굶긴다.
- **큐 용량을 유한하게**: 무한 큐(`LinkedBlockingQueue` 기본)는 장애를 메모리 문제로 바꾼다. 유한 큐는 한계를 **거절**로 드러낸다.
- **거절 카운터**: 거절이 조용히 일어나면 알림 유실을 아무도 모른다. 지표로 세고 로그를 남긴다.
- **스레드 이름**: 스레드 덤프에서 "이 스레드가 뭘 하다 막혔는지" 바로 보인다.
- **종료 대기**: 배포·재시작 시 큐에 남은 알림을 최대 20초 동안 마무리한다.

`ThreadPoolExecutor`의 동작 순서도 알고 있어야 한다. **코어 스레드 → 큐 → 최대 스레드 → 거절** 순이다. 큐가 크면 최대 스레드는 사실상 안 쓰인다. 그래서 "큐 500, 최대 4"는 "버스트를 큐로 흡수하고, 그래도 넘치면 거절한다"는 선택이다.

## 5. 실제로 어떻게 바뀌었나

수신자 10명, 모의 지연 50ms, 1 req/s, 3회 반복 측정이다.

| 반복 | 개선 전 p50 | 개선 후 p50 | 개선 전 SQL | 개선 후 SQL |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 876 ms | 21 ms | 24건 | 14건 |
| 2 | 866 ms | 17 ms | 24건 | 14건 |
| 3 | 850 ms | 16 ms | 24건 | 14건 |

모의 지연을 200ms로 올린 단건 측정에서는 2,445ms → 42ms였다. 개선 전에는 응답 시간이 지연 × 수신자 수만큼 늘어났지만, 개선 후에는 지연을 바꿔도 응답이 거의 변하지 않는다. 그게 "요청 경로에서 빠졌다"의 정의다.

SQL이 24건에서 14건으로 준 것은 수신자별 토큰 조회 10건이 `in` 절 1건으로 합쳐지고, 그 1건마저 요청 스레드가 아닌 디스패치 스레드에서 실행되기 때문이다.

**그리고 반드시 함께 말해야 하는 수치가 있다.**

| 실행 | 생성된 상품 | 디스패치 완료 | 전송 메시지 | 거절 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 242 | 242 | 2,420 | 0 |
| 2 | 242 | 242 | 2,420 | 0 |
| 3 | 241 | 241 | 2,410 | 0 |

생성된 상품 수와 디스패치 완료 수가 정확히 같고, 상품당 메시지 10건이 전부 성공했다. 응답이 빨라진 만큼 일이 뒤로 밀린 게 아니라는 근거다.

## 6. 무엇을 잃었고 어떻게 관측하는가

비동기로 옮기면 **실패가 사용자에게 보이지 않는다.** 이건 이득이 아니라 위험이다. 그래서 지표를 같이 만들었다.

| 지표 | 의미 |
| --- | --- |
| `fcm.dispatch{outcome}` | 전송 작업 성공/실패 건수 |
| `fcm.dispatch.duration` | 작업 처리 시간 |
| `fcm.executor.rejected` | 큐가 꽉 차서 거절된 건수 |
| `executor.queued`, `executor.active`, `executor.pool.size` | 큐 깊이·활성 스레드·풀 크기. Spring Boot가 `ThreadPoolTaskExecutor` 빈을 자동 바인딩한다 |
| `local.fcm.completed{outcome}` | 로컬 측정용 메시지 단위 완료 수 |

그리고 부하 테스트가 끝난 뒤 **큐에 남은 작업이 0인지**를 확인한다. API 응답이 빨라진 대신 뒤에 일이 쌓여 있으면 개선이 아니다.

### 지표를 붙였다고 관측되는 게 아니다

처음에는 executor 지표를 직접 등록했다.

```java
executor.initialize();     // 풀 A 생성
ExecutorServiceMetrics.monitor(registry, executor.getThreadPoolExecutor(), ...);  // 풀 A에 게이지 연결
```

측정해 보니 `executor_queued_tasks`가 NaN, `executor_completed_tasks_total`이 0이었다. 그런데 전송은 정상이었고 `fcm_dispatch_total`은 제대로 올라가고 있었다.

원인은 `initialize()`를 직접 호출한 것이었다. 스프링이 빈을 초기화하며 `afterPropertiesSet()`에서 `initialize()`를 다시 호출해 **새 풀 B**를 만들고, 내가 지표를 연결해 둔 풀 A는 버려졌다. Micrometer 게이지는 대상을 약한 참조로 잡기 때문에 풀 A가 GC되면서 게이지가 전부 NaN이 됐다.

수동 초기화와 수동 등록을 걷어내자 Spring Boot의 `TaskExecutorMetricsAutoConfiguration`이 살아 있는 풀을 바인딩했다.

여기서 얻은 규칙: **지표가 0인 것과 지표가 아예 없는 것, 값이 NaN인 것은 전부 다른 상태다.** 비동기 작업에서는 "안 나온다"가 "문제 없다"처럼 보이기 때문에 더 조심해야 한다.

## 7. 여기서 멈춘 이유 — 안 한 것들

- **재시도**: 지금은 실패하면 로그와 지표만 남는다. 재시도를 넣으려면 중복 알림 방지(멱등성)를 같이 설계해야 한다.
- **outbox 패턴**: 애플리케이션이 죽으면 큐의 작업은 사라진다. DB에 발송 대기 레코드를 남기고 별도 워커가 처리하면 살릴 수 있지만, 테이블·워커·정리 작업이 늘어난다.
- **메시지 브로커**: 규모가 더 커지면 필요하다. 지금 규모에서는 운영 비용이 더 크다.

"안 했다"가 아니라 **"이런 트레이드오프 때문에 지금은 안 했고, 어떤 신호가 보이면 하겠다"**라고 말할 수 있어야 한다.

## 8. 면접에서 나올 수 있는 질문

**Q. `sendAsync`를 쓰고 있었는데 왜 동기라고 판단했나요?**
`.get()`이 붙어 있었습니다. Future를 기다리는 호출이라 호출 스레드가 블로킹됩니다. 완료되지 않은 Future를 주입해서 호출이 반환되지 않는 걸 테스트로 확인했습니다.

**Q. `@Async`만 붙이면 되지 않나요? 왜 이벤트를 쓰나요?**
`@Async`만 붙이면 트랜잭션 커밋 전에 다른 스레드에서 전송이 시작됩니다. 롤백되면 유령 알림이 나가고, 커밋 전이라 새 스레드에서는 아직 조회되지 않는 데이터도 있습니다. `@TransactionalEventListener(AFTER_COMMIT)`로 커밋 이후를 보장한 뒤 `@Async`로 스레드를 분리했습니다.

**Q. 커밋 후에 전송이 실패하면 알림은 유실되는 것 아닌가요?**
맞습니다. 그래서 실패·거절을 지표로 노출했습니다. 완전히 보장하려면 outbox 패턴이 필요한데, 현재 요구사항(키워드 알림 1회 통지)에서는 중복 알림 위험과 운영 비용을 감안해 지금 단계에서는 관측 가능성 확보까지만 했습니다.

**Q. 스레드풀 크기는 어떻게 정했나요?**
컨테이너에 CPU 2개를 할당한 환경이고, 이 작업은 CPU가 아니라 네트워크 대기가 대부분이라 코어 2·최대 4로 시작했습니다. 중요한 건 절대값보다 큐를 유한하게 두고 거절을 관측 가능하게 만든 것이라고 생각합니다. 실제 값은 큐 깊이와 거절 지표를 보고 조정할 계획입니다.

**Q. 응답이 빨라진 만큼 일이 뒤로 밀린 것 아닌가요?**
그래서 응답 시간만 보지 않고, 부하 종료 후 큐 잔량과 전송 완료 건수를 같이 확인했습니다. 응답이 빨라졌는데 완료량이 줄었다면 개선이 아니라 은폐입니다.
