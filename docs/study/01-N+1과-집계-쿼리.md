# 01. N+1과 집계 쿼리

이 문서는 찜 목록 조회에서 실제로 만난 문제를 기준으로 정리한다. 코드는 `LikeRepositoryImpl.findAllByUserId`, 측정값은 [결과 문서](../result/로컬_기능_테스트_페이지.md)에 있다.

## 1. N+1이란 무엇인가

목록을 1번 조회한 뒤, 목록의 각 항목마다 추가 쿼리를 N번 더 실행하는 현상이다. 총 1 + N번의 쿼리가 나간다.

JPA에서 흔한 발생 경로는 세 가지다.

1. **지연 로딩 접근**: `@ManyToOne(fetch = LAZY)` 연관을 목록 순회 중에 건드리면 프록시가 초기화되며 항목마다 SELECT가 나간다.
2. **컬렉션 접근**: `@OneToMany` 컬렉션을 항목마다 `size()`나 순회로 접근한다.
3. **명시적 루프 쿼리**: 코드가 직접 `for` 안에서 리포지토리를 호출한다.

이 프로젝트의 사례는 3번이었다. 즉 JPA가 몰래 만든 쿼리가 아니라, 사람이 명시적으로 작성한 루프였다.

## 2. 이 프로젝트에서 실제로 일어난 일

개선 전 코드의 구조는 이랬다.

```java
// 메인 쿼리: like × chatRoom 조인 후 like.likeId로 그룹핑
.select(Projections.constructor(LikeSearchResponseDto.class,
    like.likeId,
    new QItemSearchResponseDto(..., chatRoom.countDistinct().intValue(),
        like.count().intValue(), ...)))
.from(like)
.leftJoin(like.item, item)
.leftJoin(chatRoom).on(chatRoom.item.eq(like.item))
.groupBy(like.likeId)

// 그리고 결과를 순회하며 항목마다 다시 조회
content.forEach(dto -> {
    Integer likeCount = queryFactory.select(like.countDistinct().intValue())
        .from(item).where(item.itemId.eq(dto.getItem().getItemId()))
        .leftJoin(like).on(like.item.eq(item))
        .groupBy(item.itemId).fetch().get(0);
    dto.getItem().setLikeCount(likeCount);
});
```

여기서 중요한 건 **왜 루프가 생겼는가**다.

메인 쿼리는 `group by like.likeId`로 그룹을 나눈다. 즉 그룹 하나가 "찜 한 건"이다. 그 상태에서 `like.count()`를 세면 그 값은 "이 상품을 찜한 총 사용자 수"가 아니라 조인 결과 안에서 그 그룹에 속한 행의 수다. 채팅방을 조인했으므로 그 값은 사실상 채팅방 개수에 가깝다.

값이 틀리니까 뒤에서 루프를 돌며 올바른 값으로 덮어썼다. **N+1은 원인이 아니라 증상이었고, 진짜 원인은 집계 단위를 잘못 잡은 쿼리였다.**

이걸 이해하고 말하는 것과, "N+1이 있어서 fetch join을 했습니다"라고 말하는 것은 완전히 다르다. 면접에서는 이 차이가 드러난다.

## 3. 조인 후 그룹핑이 왜 위험한가

한 상품에 채팅방이 3개, 찜이 4개 있다고 하자.

```
item ⟕ chat_room ⟕ likes
```

이 조인의 중간 결과는 3 × 4 = 12행이다. 상품 1건을 위해 12행을 만들고 그다음 `group by`로 다시 1행으로 줄인다. 이 "부풀렸다가 줄이기"가 비용이다. 페이지에 상품 10건이 있고 각각 채팅방 5개·찜 20개면 중간 결과는 1,000행이 된다.

`countDistinct()`를 쓰면 **값은** 맞출 수 있다. 중복 행을 제거하고 세기 때문이다. 하지만 **비용은** 그대로다. 값이 맞다고 해서 쿼리가 싸진 게 아니다.

이 프로젝트의 상품 검색(`itemSearch`)이 정확히 이 구조이고, 측정에서 요청당 SQL이 3건뿐인데도 DB 시간이 평균 69ms였다. 쿼리 개수가 적다고 빠른 게 아니라는 증거다.

## 4. 해결 수단들과 선택 기준

| 방법 | 쓰는 경우 | 한계 |
| --- | --- | --- |
| fetch join | 연관 **엔티티**가 필요할 때 | 컬렉션 fetch join은 페이징과 함께 쓰면 Hibernate가 메모리에서 페이징(과거 HHH000104 경고). 둘 이상의 컬렉션은 MultipleBagFetchException |
| `@EntityGraph` | fetch join과 같은 목적, 선언적으로 | 위와 동일한 제약 |
| `@BatchSize` / `default_batch_fetch_size` | 지연 로딩 N+1을 N/배치크기로 줄일 때 | 쿼리를 없애는 게 아니라 줄이는 것. IN 절 크기 관리 필요 |
| **상관 서브쿼리 집계** | 목록에 **개수**만 필요할 때 | 행마다 서브쿼리 평가. 조인 컬럼 인덱스가 없으면 느림 |
| 파생 테이블 조인(group by 후 join) | 집계 대상이 크고 재사용될 때 | JPQL 표현이 제한적, 네이티브 쿼리로 가기 쉬움 |
| 2단계 조회(ID 조회 → 집계 일괄 조회) | 위 방법이 다 애매할 때 | 쿼리 2~3개 고정, 조립 코드가 늘어남 |

이번에 고른 건 **상관 서브쿼리 집계**다. 이유는 세 가지다.

1. 목록에 필요한 건 엔티티가 아니라 **개수**뿐이다. 엔티티를 끌어올 이유가 없다.
2. 조인으로 부풀렸다가 그룹핑하는 구조 자체를 없앨 수 있다.
3. 페이징(`offset`/`limit`)이 DTO 프로젝션 위에서 안전하게 동작한다. 컬렉션 fetch join이었다면 페이징이 깨졌을 것이다.

개선 후 코드:

```java
QChatRoom chatRoomCount = new QChatRoom("chatRoomCount");
QLike likeCount = new QLike("likeCount");

new QItemSearchResponseDto(..., 
    JPAExpressions.select(chatRoomCount.count().intValue())
        .from(chatRoomCount).where(chatRoomCount.item.eq(item)),
    JPAExpressions.select(likeCount.count().intValue())
        .from(likeCount).where(likeCount.item.eq(item)), ...)
.from(like)
.leftJoin(like.item, item)
.leftJoin(item.user, user)
```

별칭을 새로 만든 이유(`new QLike("likeCount")`)도 설명할 수 있어야 한다. 바깥 쿼리의 `like`와 서브쿼리의 `like`가 같은 별칭이면 상관 서브쿼리가 아니라 자기 자신을 참조하게 된다.

## 5. 실제로 어떻게 바뀌었나

상품 10만·찜 50만 건, 10 req/s, 워밍업 1분 + 측정 3분, 3회 반복 조건의 실측값이다.

| 페이지 크기 | 요청당 SQL | SQL 시간 | p50 | p95 |
| ---: | --- | --- | --- | --- |
| 10 | 13 → 2건 | 3.4 → 1.0 ms | 8.4 → 5.3 ms | 10.5 → 6.6 ms |
| 50 | 53 → 2건 | 8.5 → 1.2 ms | 16.0 → 5.7 ms | 24.0 → 7.6 ms |
| 100 | 103 → 2건 | 15.1 → 1.4 ms | 25.6 → 6.1 ms | 34.7 → 7.9 ms |

숫자 하나만 외운다면 **"페이지 크기를 10배로 늘렸을 때 응답 시간이 3배가 되던 것이 거의 평평해졌다"** 를 외운다. 절대값보다 기울기가 바뀐 것이 이 작업의 결과다.

## 6. "쿼리 수가 줄었다"는 왜 그 자체로 중요한가

쿼리 1건은 단순히 SQL 실행 시간만 쓰는 게 아니다. 매 쿼리마다

- 커넥션 풀에서 커넥션을 쓰는 시간이 늘어나고(풀 고갈의 원인),
- 네트워크 왕복(로컬이라도 TCP 왕복)이 발생하고,
- JDBC 문장 파싱·바인딩·결과 매핑 비용이 들고,
- 영속성 컨텍스트에 엔티티가 쌓인다.

그래서 "SQL 시간 총합"만 보면 작아 보여도, 동시 요청이 늘면 커넥션 점유 시간이 곱해져서 처리량 한계로 나타난다. 이번 측정에서 페이지 크기 100일 때 요청당 SQL 103건, SQL 시간 15ms였는데, 이 요청이 초당 수십 건 들어오면 커넥션 10개짜리 풀에서 대기가 생긴다.

## 7. 면접에서 나올 수 있는 질문

**Q. N+1을 어떻게 발견했나요?**
페이지 크기를 10, 50, 100으로 바꿔가며 요청당 JDBC 실행 수를 측정했습니다. 13건, 53건, 103건으로 정확히 항목당 1건씩 늘었습니다. 요청마다 헤더로 SQL 실행 수를 내려주는 필터를 로컬 프로필에 붙여서, 응답을 볼 때 같이 확인할 수 있게 했습니다.

**Q. 왜 fetch join을 쓰지 않았나요?**
필요한 게 연관 엔티티가 아니라 개수였기 때문입니다. 그리고 컬렉션을 fetch join하면서 페이징을 하면 Hibernate가 전체를 읽어 메모리에서 잘라내기 때문에, 목록 API에는 맞지 않습니다.

**Q. 상관 서브쿼리는 행마다 실행되는데 그게 더 빠른가요?**
행 수가 페이지 크기로 제한되기 때문에 최대 100회입니다. 그리고 각 서브쿼리는 `item_id` 조건 하나짜리 집계라 인덱스가 있으면 싸게 끝납니다. 반대로 기존 방식은 조인으로 중간 행을 만들고 다시 그룹핑했고, 거기에 항목당 왕복 쿼리까지 더했습니다. 다만 서브쿼리 방식도 조인 컬럼 인덱스가 없으면 느려지므로 실행 계획을 확인해야 합니다.

**Q. 결과가 같다는 건 어떻게 보장했나요?**
개선 전후로 같은 데이터에 같은 요청을 보내 응답 본문을 비교했고, 삭제된 상품 제외·다음 페이지 여부·찜 수·채팅 수를 검증하는 테스트를 유지했습니다. 그리고 "페이지 크기와 무관하게 쿼리 수가 같다"는 조건을 테스트로 고정해서, 나중에 누가 루프를 다시 넣으면 실패하도록 했습니다.

**Q. 더 개선할 여지는요?**
같은 구조가 상품 검색과 관리자 목록에도 남아 있습니다. 측정에서 관리자 목록은 상품 10만 건에서 단건 요청이 약 0.5초였고, 초당 10건을 보내면 처리량이 0.8건으로 떨어지며 15초 타임아웃이 발생했습니다. 다음 작업으로 같은 방식을 적용하고, `item(campus_id, is_deleted, created_date)` 같은 복합 인덱스를 실행 계획으로 검증할 계획입니다.
