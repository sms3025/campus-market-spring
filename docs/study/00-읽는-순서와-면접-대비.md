# 00. 읽는 순서와 면접 대비

이 폴더는 캠퍼스 마켓 프로젝트에서 진행한 성능 개선 작업을 **직접 설명할 수 있게** 만들기 위한 학습 노트다. 문서마다 "이 프로젝트에서 실제로 무슨 일이 있었는지 → 왜 그게 문제인지 → 어떻게 고쳤는지 → 예상 질문과 답변" 순으로 정리했다.

측정 근거는 [결과 문서](../result/로컬_기능_테스트_페이지.md), 남은 과제는 [후속 계획](../plan/후속_성능_고도화_계획.md)에 있다.

먼저 04번을 읽는 이유가 있다. 면접에서 성능 이야기가 나오면 거의 항상 **"그걸 어떻게 확인했나요?"**로 이어진다. 측정 방법을 먼저 설명할 수 있으면 나머지 이야기의 신뢰도가 달라진다.

## 이 작업을 한 문장으로 말하면

> 개인 포트폴리오로 확장한 fork 저장소에서, 제가 기여했던 상품·찜·키워드·알림 경로에 로컬 성능 측정 환경을 만들고, 측정으로 찾은 세 가지 문제(찜 목록 N+1, 전체 키워드 메모리 스캔, 알림 전송의 요청 스레드 블로킹)를 고친 뒤 같은 조건으로 재측정했습니다.

## 30초 버전

측정 환경을 먼저 만들었습니다. Docker로 DB·앱·모니터링을 묶고 자원을 고정한 뒤, 상품 10만·찜 50만 규모 데이터를 재현 가능하게 적재하고, k6로 고정 도착률 부하를 걸었습니다. 요청별 SQL 실행 수도 헤더로 볼 수 있게 했습니다.

그 상태에서 세 가지가 나왔습니다. 찜 목록은 페이지 크기 10·50·100에서 SQL이 13·53·103건으로 항목당 1건씩 늘었고, 상품 등록은 키워드 2만 건을 매번 전부 메모리로 읽고 있었고, 알림 전송은 `sendAsync().get()`으로 요청 스레드를 트랜잭션 안에서 붙잡고 있었습니다.

각각 집계 서브쿼리, DB 조건 이동, 커밋 후 비동기 발행으로 고쳤고, 같은 데이터·같은 부하로 다시 측정해서 전후를 비교했습니다.

## 준비할 때 주의할 점

1. **숫자를 외우지 말고 구조를 외운다.** "13·53·103"은 결론이 아니라 증거다. 핵심은 "반환 항목 수에 비례해 쿼리가 늘었다"는 구조다.
2. **모르는 건 모른다고 한다.** 이 작업에서 재시도·outbox는 하지 않았다. "왜 안 했는지"를 설명할 수 있으면 충분하다.
3. **한계를 먼저 말한다.** 단일 로컬 장비 측정이고, 절대 수치를 운영 성능으로 주장하지 않는다. 이 선을 스스로 그으면 오히려 신뢰를 얻는다.
4. **남은 과제를 안다.** 상품 검색과 관리자 목록에는 같은 구조가 남아 있다. 측정값(관리자 목록 단건 0.5초, 10 req/s에서 처리량 0.8 req/s)과 계획을 함께 말하면 작업이 끝나지 않았다는 게 약점이 아니라 로드맵이 된다.
