# 02. 필터링은 어디서 할 것인가

이 문서는 상품 등록 시 키워드 알림 대상을 고르는 코드에서 만난 문제를 기준으로 정리한다. 코드는 `KeywordService.findKeywordsWithSameItemCampusAndTitle`이다.

## 1. 문제가 된 코드

```java
return keywordRepository.findKeywordsWithUserAndCampus()   // 조건 없는 전체 조회
    .stream()
    .filter(k -> k.getUser().getCampus() != null)
    .filter(k -> !Objects.equals(k.getUser().getUserId(), savedItem.getUser().getUserId()))
    .filter(k -> Objects.equals(k.getUser().getCampus().getCampusId(), savedItem.getCampus().getCampusId()))
    .filter(k -> savedItem.getTitle().contains(k.getKeywordName()))
    .toList();
```

쿼리에는 `where`가 없다. 전체 키워드를 사용자·캠퍼스와 함께 읽어온 뒤 자바에서 네 번 거른다.

medium 데이터 기준 키워드는 20,010건이다. 상품을 한 건 등록할 때마다 20,010건을 읽고, 그중 실제 알림 대상은 보통 0~10건이다. **결과가 0건이어도 비용은 그대로 낸다.**

## 2. 왜 나쁜가 — 네 가지 층위

### (1) 전송량과 매핑 비용
DB가 20,010행을 반환하면 JDBC가 그만큼 읽고, Hibernate가 엔티티 20,010개를 만들고, 영속성 컨텍스트에 올린다. `join fetch`가 두 개 붙어 있으니 User와 Campus까지 함께 만든다. 필터링에 쓰이고 즉시 버려질 객체들이다.

### (2) 메모리와 GC
요청당 수만 개의 단명 객체가 생긴다. 동시 요청이 늘면 young generation이 빠르게 차고 GC 빈도가 올라간다. GC 시간은 모든 요청의 지연에 얹힌다.

### (3) 인덱스를 쓸 기회 자체를 버림
`where`가 없으므로 DB는 무조건 전체 스캔이다. 캠퍼스 조건을 DB로 내리면 `keyword`에서 사용자를 타고 캠퍼스로 좁힐 수 있고, 인덱스 설계의 여지가 생긴다. 애플리케이션에서 거르면 그 여지 자체가 없다.

### (4) 확장성의 방향이 틀림
사용자가 늘면 키워드도 는다. 즉 이 비용은 **서비스가 성공할수록 커진다.** 상품 등록이라는 핵심 쓰기 경로에 그런 성질의 비용이 있으면 안 된다.

## 3. 어떻게 고쳤나

```java
@Query("select k from Keyword k "
    + "join fetch k.user u "
    + "join fetch u.campus c "
    + "where c.campusId = :campusId "
    + "and u.userId <> :writerId "
    + "and locate(k.keywordName, :title) > 0")
List<Keyword> findMatchingKeywords(Long campusId, Long writerId, String title);
```

서비스는 이렇게 남았다.

```java
return keywordRepository.findMatchingKeywords(campusId, writerId, title)
    .stream()
    .filter(k -> savedItem.getTitle().contains(k.getKeywordName()))
    .toList();
```

### 자바 필터를 하나 남긴 이유

`locate`는 DB collation을 따른다. 이 프로젝트의 MariaDB는 `utf8mb4_unicode_ci`라서 **대소문자를 구분하지 않는다.** 반면 기존 자바 코드의 `String.contains`는 **구분한다.**

그대로 두면 "Camera"를 등록한 사용자가 "sony camera"라는 제목에도 알림을 받게 된다. 동작이 바뀌는 것이다. 성능 개선 작업에서 동작이 조용히 바뀌는 건 가장 나쁜 종류의 버그다.

그래서 이렇게 정리했다.

- DB의 `locate` 결과는 자바 `contains` 결과의 **상위 집합**이다(대소문자 구분을 안 하니 더 많이 잡힌다).
- 상위 집합에 원래의 정확한 조건을 한 번 더 적용하면 **원래 결과와 정확히 같다.**
- 후보가 이미 수십 건 이하로 줄었으므로 이 필터의 비용은 무시할 수 있다.

이 논리를 테스트로도 고정했다. `KeywordServiceTest`에서 리포지토리가 "Camera"와 "camera"를 모두 반환하도록 두고, 서비스가 "camera"만 남기는지 검증한다.

### 실제로 어떻게 바뀌었나

부하 없이 상품 등록을 20회 호출한 단건 측정값이다. 수신자 수(10명)는 두 조건에서 같다.

| 데이터 | 키워드 수 | 개선 전 p50 | 개선 후 p50 | 요청당 SQL |
| --- | ---: | ---: | ---: | --- |
| smoke | 210건 | 44.5 ms | 35.4 ms | 24 → 14건 |
| medium | 20,010건 | 379.1 ms | 39.5 ms | 24 → 14건 |

개선 전에는 키워드가 약 100배 늘 때 등록 비용이 8.5배가 됐다. 개선 후에는 1.1배다. **비용이 전체 키워드 수에 비례하던 성질 자체가 사라진 것**이 결과다.

주의할 점도 같이 말해야 한다. 두 데이터셋은 키워드 수뿐 아니라 상품 수도 다르다(1,000건 대 100,000건). 그래서 "키워드 수만의 효과"라고 단정하지 않고, "데이터 규모에 따른 등록 비용 증가가 사라졌다"로 말하는 게 정확하다.

## 4. `like '%키워드%'`와 인덱스

`locate(k.keywordName, :title) > 0`은 "제목 안에 키워드가 들어 있는가"다. 컬럼 값이 상수 안에 포함되는지를 보는 형태라 키워드 컬럼 인덱스로 범위 탐색을 할 수 없다.

반대 방향인 상품 검색의 `title like '%검색어%'`도 마찬가지다. 선행 와일드카드가 있으면 B-Tree 인덱스는 쓸 수 없다. B-Tree는 "앞에서부터 정렬된" 구조라 앞부분을 모르면 탐색 시작점을 잡지 못한다.

그래서 중요한 건 **"인덱스를 못 타는 조건을 몇 행에 대해 평가하느냐"**다.

- 개선 전: 전체 키워드(20,010행)에 대해 자바에서 평가
- 개선 후: 캠퍼스·작성자 조건으로 줄인 행에 대해 DB에서 평가

인덱스를 못 타는 조건을 없앤 게 아니라, **그 조건을 평가할 대상을 줄인 것**이다. 이 구분을 말할 수 있으면 "무조건 인덱스" 수준의 답변과 차별화된다.

더 줄이려면 `keyword(user_id)`와 `users(campus_id)` 인덱스로 후보 축소를 빠르게 하거나, 전문 검색(FULLTEXT)·n-gram 색인을 도입하는 방법이 있다. 다만 FULLTEXT는 부분 일치 규칙이 달라지므로 요구사항 변경을 동반한다.

## 5. 일반화 — 언제 애플리케이션에서 거르나

DB로 내리는 게 기본이지만 항상은 아니다.

| 상황 | 선택 |
| --- | --- |
| 조건이 SQL로 표현 가능하고 선택도가 높다 | DB |
| 전체 데이터가 작고 고정적이다(코드 테이블 등) | 캐시 + 애플리케이션 |
| 조건이 외부 호출·복잡한 도메인 규칙이다 | 애플리케이션 (단, 대상은 DB에서 최대한 줄인 뒤) |
| 정확도 보정이 필요하다(collation, 정규화 차이) | DB로 후보 축소 + 애플리케이션에서 정밀 필터 ← 이번 사례 |

## 6. 면접에서 나올 수 있는 질문

**Q. 이 문제를 어떻게 알아챘나요?**
상품 등록 경로를 읽다가 리포지토리 메서드에 `where`가 없는 걸 봤습니다. 조건이 전부 스트림 필터에 있었습니다. 그래서 키워드 수가 다른 두 데이터셋(20,010건 / 210건)을 각각 적재하고 상품 등록 단건 응답 시간을 비교했습니다.

**Q. `contains`를 왜 남겼나요? 중복 아닌가요?**
DB의 `locate`는 collation 때문에 대소문자를 구분하지 않아서, 그대로 두면 알림 대상이 늘어납니다. 성능 개선이 동작 변경을 동반하면 안 된다고 생각했습니다. DB 결과가 원래 조건의 상위 집합이라는 걸 확인하고, 좁혀진 후보에만 원래 조건을 적용해서 결과 동일성을 지켰습니다.

**Q. 대소문자 무시가 오히려 맞는 동작 아닌가요?**
그럴 수 있습니다. 다만 그건 기획 결정이라 성능 작업에 섞어서 바꾸면 안 된다고 판단했습니다. 바꾸려면 별도 변경으로 제안하고 테스트를 그에 맞게 바꾸는 게 맞습니다.

**Q. 인덱스는 추가했나요?**
이번 변경에서는 추가하지 않았습니다. 조건을 DB로 내린 것만으로 얼마나 줄어드는지 먼저 측정하고, 인덱스는 실행 계획을 근거로 다음 단계에서 판단하려고 했습니다. 근거 없이 인덱스를 늘리면 쓰기 비용만 늘어납니다.
