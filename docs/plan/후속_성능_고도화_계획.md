# 후속 성능 고도화 계획

- 작성일: 2026-09-12, 갱신: 2026-09-13
- 작업 주체: 이정태(sms3025)의 fork 저장소 개인 포트폴리오 고도화
- 상태: P1~P3 구현·검증 완료, P4~P6 계획 상태(사용자 승인 대기)
- 선행 문서: [로컬 기능 테스트 페이지 계획](로컬_기능_테스트_페이지.md), [측정 결과](../result/로컬_기능_테스트_페이지.md)

## 1. 이 문서의 위치

로컬 측정 환경에서 확보한 baseline으로 여섯 가지 문제를 정리했고, 그중 세 가지(P1~P3)를 실제로 고쳐 같은 조건으로 재측정했다. 이 문서는 완료된 작업의 결과와 남은 작업의 계획을 함께 담는다.

측정하지 않은 개선율은 쓰지 않는다. 완료 항목의 수치는 전부 실측이고, 남은 항목의 기대 효과는 "무엇이 줄어드는지"를 구조로만 설명한다.

## 3. 완료된 작업 (P1~P3)

측정 조건과 원본 수치는 [결과 문서 4.5~4.7절](../result/로컬_기능_테스트_페이지.md)에 있다.

| 항목 | 핵심 변경 | 측정 결과 |
| --- | --- | --- |
| P1 | 조인 후 그룹핑 + 항목별 재조회를 상품 기준 상관 서브쿼리 집계로 교체 | 요청당 SQL 13/53/103건 → 2/2/2건, p50 8.4/16.0/25.6ms → 5.3/5.7/6.1ms |
| P2 | 캠퍼스·작성자·제목 조건을 JPQL `where`로 이동, 대소문자 판정만 애플리케이션에 유지 | 키워드 20,010건 데이터에서 등록 p50 379.1ms → 39.5ms. 키워드 210건 대비 비용 차이가 8.5배 → 1.1배 |
| P3 | 커밋 이후 전용 executor 디스패치, 토큰 조회 N→1, `sendEach` 배치 전송 | 등록 p50 876ms → 16ms(지연 50ms·수신자 10명), 요청당 SQL 24건 → 14건. 디스패치 완료 수 = 생성 상품 수, 거절 0건 |

### 완료 항목에서 남긴 판단

- **재시도·outbox는 넣지 않았다.** 중복 알림 방지 설계가 함께 필요하다. 지금은 실패·거절·잔여 작업을 관측할 수 있는 상태까지만 만들었다. 운영에서 유실이 실제로 관측되면 그때 근거를 갖고 도입한다.
- **알림 이력 저장은 트랜잭션 안에 남겼다.** 이력은 등록의 일부이므로 커밋 단위를 함께 가져가는 편이 맞다고 판단했다. 다만 수신자 수만큼 개별 insert가 나가므로, fan-out이 커지면 P7 후보가 된다.
- **인덱스는 추가하지 않았다.** 조건을 쿼리로 내린 효과만 먼저 측정했다. 인덱스는 실행 계획을 근거로 다음 단계에서 판단한다.

## 4. 남은 작업

### 4.1 P4 · 목록 조회의 집계 조인 정리 (1순위)

`itemSearch`와 `adminItemSearch`는 `item ⟕ chat_room ⟕ likes`를 조인한 뒤 `group by item.itemId`로 묶는다. 상품 1건에 채팅방 c건·찜 l건이면 그룹핑 전 중간 결과가 c×l 행이 된다. `countDistinct`로 값은 맞지만 비용은 그대로 지불한다.

측정된 현재 상태(상품 10만 건, 페이지 크기 10):

| 시나리오 | 요청당 SQL | SQL 시간 | p50 | 한계 |
| --- | ---: | ---: | ---: | --- |
| 상품 검색 10 RPS | 3건 | 62 ms | 65 ms | 정상 |
| 상품 검색 30 RPS | 3건 | 561 ms | 11,403 ms | 실제 17.3 RPS, 오류 5%, 미시작 1,023건 |
| 관리자 목록 1 RPS | 2건 | 500 ms | 502 ms | 정상이지만 단건 0.5초 |
| 관리자 목록 10 RPS | 2건 | 5,681 ms | 9,992 ms | 실제 0.8 RPS, 오류 5.6% |

**쿼리 개수가 아니라 단일 쿼리 비용이 처리량 한계를 만든다.** 요청당 SQL이 2~3건뿐인데 그 시간이 응답 시간의 대부분이다.

변경 방향은 P1과 동일하다. 채팅방·찜 집계를 상품 기준 상관 서브쿼리 또는 파생 테이블 조인으로 옮기고, 조인 후 그룹핑 구조를 제거한다. `isLiked`는 현재 상관 서브쿼리 `exists`이며, 대상 사용자 찜 목록과의 조인으로 대체 가능한지 실행 계획으로 비교한다.

완료 기준: 응답 본문 동일(찜 수·채팅 수·isLiked·삭제 상품 제외·hasNext), 같은 부하 조건에서 p50/p95 개선과 목표 RPS 달성, `EXPLAIN ANALYZE` 전후 기록.

### 4.2 P5 · 검색어 조건과 인덱스 (2순위)

`containsIgnoreCase`는 `lower(title) like '%검색어%'`가 되어 선행 와일드카드 때문에 B-Tree 인덱스를 쓸 수 없다. 이 조건 자체를 없앨 수는 없으므로, 평가 대상 행을 줄이는 것이 목표다.

- `item(campus_id, is_deleted, created_date, item_id)` 복합 인덱스로 후보를 먼저 좁힐 수 있는지 실행 계획으로 확인한다.
- `likes(item_id)`, `chat_room(item_id)`는 P4의 집계 서브쿼리가 타야 하는 인덱스다. P4와 함께 검증한다.
- FULLTEXT·n-gram 도입은 부분 일치 규칙이 달라지므로 요구사항 변경을 동반한다. 별도 판단 항목으로 둔다.

인덱스는 추측으로 추가하지 않는다. 추가 전후로 조회와 **상품 등록 시나리오를 함께** 측정해 쓰기 비용 증가를 확인한다.

### 4.3 P6 · 깊은 페이지 (3순위)

offset 페이지네이션은 건너뛰는 행에 비례해 비용이 는다. 현재 측정은 첫 페이지 위주였으므로, 먼저 `-Page` 옵션으로 깊은 페이지 비용을 측정해 문제 크기를 확인한다. 실제로 문제가 확인되면 정렬 키 기반 no-offset 방식을 검토하되, API 응답 형식이 바뀌므로 클라이언트 영향 검토가 선행되어야 한다.

### 4.4 관측·자원 관련 후보

근거가 관측될 때만 진행한다.

| 후보 | 착수 신호 |
| --- | --- |
| Hikari 풀 크기 조정 | DB 활성/대기 커넥션 지표에서 대기가 관측될 때 |
| 알림 이력 일괄 저장 | fan-out이 커져 개별 insert가 등록 지연에 기여할 때 |
| 알림 재시도·outbox | 전송 실패·거절 지표가 0이 아닐 때 |
| 조회 캐시 | 동일 조건 재조회 비율이 높고 정합성 요구가 허용될 때 |
| JVM/GC 옵션 | GC 시간이 응답 지연에 기여한다고 관측될 때 |

## 5. 진행 순서

1. 현재 코드로 baseline 재확인(재현성 확인).
2. P4 구현. 결과 동등성 테스트를 먼저 작성한다.
3. P4 측정 후 P5 인덱스 검증. 조회와 등록을 함께 측정한다.
4. 깊은 페이지 비용 측정 → 필요 시 P6.
5. 전후 비교를 결과 문서에 추가하고 사용자 허락을 받아 커밋한다.

각 단계는 독립 커밋으로 나눈다. 한 커밋에 여러 최적화를 섞으면 전후 비교의 원인 귀속이 불가능해진다.

## 6. 측정 프로토콜

- 데이터: 동일 seed manifest(medium, uniform, seed 3025)를 사용한다. 쓰기가 포함된 시나리오는 반복마다 Reset/Seed로 초기 상태를 복구한다.
- 부하: 워밍업 1분, 측정 3분, 동일 조건 3회. 목표/실제 요청률과 미시작 작업 수를 함께 기록한다.
- 계측: SQL 실행 수는 부하와 분리해 격리 실행으로 측정한다. latency 측정 시 SQL 본문 로깅은 끈다.
- 비교: 반복별 p95를 평균하지 않는다. 실행 폴더의 원본 summary를 근거로 제시한다.
- 환경: 동일 장비에서 DB·앱·부하 도구·모니터링이 함께 동작하는 조건을 명시한다. 운영 환경 수치로 일반화하지 않는다.

## 7. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 집계 쿼리 변경으로 응답 값이 달라짐 | 개선 전후 응답 본문 동등성 테스트를 먼저 작성하고, 삭제 상품·중복 찜·경계 페이지를 포함한다 |
| 인덱스 추가로 쓰기 성능이 저하됨 | 상품 등록 시나리오를 인덱스 전후로 함께 측정한다 |
| no-offset 전환이 클라이언트를 깨뜨림 | 응답 형식 변경 범위를 먼저 정리하고, 기존 형식과 병행 제공 가능성을 검토한다 |

| 단일 로컬 장비 측정의 변동성 | 3회 반복과 조건 기록, 이상치 발생 시 재측정 |
