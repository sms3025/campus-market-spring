# 로컬 기능 테스트 페이지 작업 계획

- 작성일: 2026-09-12
- 작업 주체: 이정태(sms3025)의 fork 저장소 개인 포트폴리오 고도화
- 상태: 사용자 구현 승인(2026-09-12), 구현 및 검증 진행 중
- 용어: 사용자 요청의 `jpq`는 저장소 기술 구성에 따라 JPA로 해석한다.

## 1. 목적과 범위

이정태(sms3025)가 기여한 기능을 중심으로 로컬 테스트 페이지와 검증 환경을 만든다. 이후 FCM 비동기 알림, JPA·Querydsl 조회, N+1 문제 해결, 테스트 커버리지 고도화의 전후 차이를 재현 가능한 근거로 남긴다.

로그인·채팅 기능의 화면 구현, 테스트 및 고도화는 제외한다. 사용자 전체 기능이나 관리자 전체 기능으로 범위를 확장하지 않는다. 원 프로젝트 기여자 표기를 유지하며 기존 기여와 이번 개인 고도화 작업을 구분한다.

이번 작업은 우선 테스트 페이지와 측정 기반을 만드는 단계다. 비동기 처리 구조 변경과 조회 최적화 자체는 기준 측정 후 별도 docs/plan 문서로 제안하고 승인을 받아 진행한다.

커밋은 해당 기능에 기여했다는 근거이며 파일 전체의 단독 작성자로 간주하지 않는다. 승인 후 세부 변경 이력과 테스트를 대조하여 API별 기여 범위를 정리한다. 찜 조회는 관련 변경 이력과 아래 N+1 후보를 기준으로 검증 대상에 포함한다.

현재 코드에서 확인한 고도화 후보:

- FcmNotificationService는 `sendAsync(message).get()`을 호출한다. 호출 스레드가 완료를 기다리므로 SDK 메서드 이름만으로 요청 흐름이 비동기라고 판단할 수 없다.
- FCM 오류 일부를 로그로 처리하므로 HTTP 성공과 FCM 전송 성공, 브라우저 수신 성공은 각각 확인해야 한다.
- LikeRepositoryImpl은 조회 결과를 순회하며 항목별 찜 개수를 추가 조회한다. 데이터 증가에 따른 쿼리 수를 측정할 N+1 후보가 있다.
- ItemRepositoryImpl은 Querydsl 조건·정렬·집계·Slice 페이지 조회를 사용한다. 조회 결과 정확성과 쿼리 비용을 함께 확인한다.
- JaCoCo 설정이 있으나 라인·브랜치 최소 기준이 현재 0.00이다. 실제 커버리지를 먼저 측정한다.
- application 설정 및 초기 CSV가 현재 작업 디렉터리에 없다. Firebase 초기화, AWS, Redis, 데이터 로더의 로컬 실행 의존성을 정리해야 한다.

## 3. 테스트 페이지

HTML/CSS/JavaScript 기반 한국어 페이지를 로컬 전용 `/local-test/` 경로에서 제공한다. 별도 프런트엔드 빌드 없이 사용하고, 입력 폼·요청 예제·응답 상태·본문·소요 시간·실행 기록을 표시한다.

| 화면 | 제공할 기능 |
| --- | --- |
| 상품·조회 | 담당 상품 API의 등록·상세·수정·삭제, 검색어·가격·카테고리·상태·정렬·페이지 크기 입력 |
| 찜 조회 | 찜 테스트 데이터 구성, 찜 목록과 집계 결과 확인, 데이터 규모별 조회 실행 |
| 키워드·FCM | 키워드 등록·조회·삭제, 타 사용자 상품 등록으로 알림 유발, 본인 알림 제외 확인 |
| Firebase 웹 수신 | 웹 설정 입력, 알림 권한 요청, 서비스 워커 등록, FCM 토큰 발급·등록, 포그라운드 수신 기록과 백그라운드 알림 |
| 담당 관리자 조회 | 상품 검색·상태 필터 및 캠퍼스 목록만 제공 |
| 검증 안내·결과 | 쿼리 측정 시나리오, FCM 관찰 결과, 생성된 JaCoCo 보고서 확인 경로와 측정 조건 |

페이지 소요 시간은 브라우저 관측값으로 표시한다. SQL 실행 횟수나 커버리지를 브라우저 시간으로 추정하지 않으며, 각각 서버 계측과 자동 테스트 결과를 사용한다. 브라우저에서 임의 명령으로 Gradle 테스트를 실행하는 API는 만들지 않는다.

인증은 테스트 준비에 필요한 최소 지원만 한다. 기존 JWT 입력 또는 로컬 프로필에서만 동작하는 고정 테스트 사용자/관리자 선택을 제공한다. Google 로그인 UI와 로그인·갱신·로그아웃 테스트, 인증 서비스 리팩터링은 제외한다. 기본 프로필의 인증 정책은 유지한다.

## 4. Firebase 웹 실제 연동 — 이번 범위에 포함

사용자는 Firebase 콘솔의 실제 웹 앱 설정을 수행한다. 구현에는 Firebase Web SDK, 서비스 워커 파일, 설정 예제, 콘솔 설정부터 브라우저 수신까지의 실행 안내를 포함한다.

사용자 준비 항목:

1. 테스트용 Firebase 프로젝트와 웹 앱 등록.
2. 웹 앱 설정값(apiKey, authDomain, projectId, storageBucket, messagingSenderId, appId 등 콘솔 제공값).
3. Web Push 인증서의 VAPID 공개 키.
4. 동일 프로젝트의 백엔드 Admin SDK 서비스 계정 파일 또는 지원되는 서버 자격증명 설정.
5. 지원 브라우저에서 localhost로 접근하고 알림 권한 허용.

서비스 계정 비밀키는 백엔드 로컬 설정으로만 사용한다. 브라우저에는 웹 앱 설정과 VAPID 공개 키만 전달한다. 서비스 워커 경로와 scope를 명시하고 로컬 테스트 범위로 제한한다. SDK와 브라우저별 설정은 구현 시 공식 문서로 확인한다.

기존 로그인 API가 FCM 토큰을 함께 저장하므로, 로그인 구현 없이 테스트 사용자에 토큰을 연결할 로컬 전용 지원 경로를 제공한다. 전송 대상은 사용자가 등록한 테스트 토큰으로 한정한다.

수신 검증은 상품·키워드 흐름을 사용하며 채팅을 트리거로 사용하지 않는다. 포그라운드 메시지, 백그라운드 알림, 제목·본문·deeplink 데이터를 확인한다. 기존 앱용 딥링크는 데이터 정확성을 검증하고 웹 클릭 이동은 허용된 로컬 URL로 연결한다. 서버 전송 완료와 브라우저 수신 결과를 따로 기록한다.

Firebase 설정 전에도 페이지와 자동 테스트를 진행할 수 있도록 모의 전송 모드를 제공하고 실제 전송과 명확히 표시한다. 실제 자격증명·사용자 권한이 필요한 수신 검증은 사용자 실행 항목으로 남길 수 있으며, 완료하지 않은 실제 수신을 성공으로 기록하지 않는다.

## 5. JPA·Querydsl·N+1 검증 기반

- MariaDB·Redis Docker Compose와 local-test 설정을 제공한다. 기존 로컬 인스턴스 사용법도 안내한다.
- 테스트 사용자, 학교, 상품, 찜, 키워드의 재현 가능한 seed를 제공한다. 조회 규모를 단계별로 늘릴 수 있게 한다.
- Querydsl 필터 조합, 가격 경계, 정렬 동률, 다음 페이지 유무, 집계 값과 삭제 상품 제외를 검증한다.
- N+1 측정은 seed 생성 후 영속성 컨텍스트를 비우고 측정 구간을 분리한다. 반환 DTO 구성까지 포함하고 인증·seed 쿼리는 조회 쿼리와 구분한다.
- 요청별 또는 격리된 통합 테스트 단위로 SQL 수를 측정한다. 전역 통계에 동시 요청이 섞인 값을 요청별 결과로 제시하지 않는다.
- 목록 규모별 SQL 수와 응답 시간을 기준값으로 기록한다. 시간 비교는 DB, 데이터, 워밍업, 반복 횟수를 함께 기록한다.
- 이번 단계에서 기존 N+1을 재현하고, 후속 최적화 작업의 완료 기준은 결과 보존과 데이터 수에 비례하는 추가 쿼리 제거로 정한다.

## 6. FCM 비동기·테스트 커버리지 검증 기반

- 지연 가능한 테스트 전송 대역을 사용해 현재 호출 대기 동작을 재현한다. 실제 Firebase 지연에 의존하는 불안정한 자동 테스트를 피한다.
- 전송 성공, INVALID_ARGUMENT, UNREGISTERED, 기타 예외, InterruptedException과 토큰 삭제 여부를 검증한다.
- 후속 비동기 고도화에서 확인할 항목은 요청 응답과 전송 완료 분리, 트랜잭션 커밋/롤백, 작업 실패 관찰, executor 용량 및 거절 처리다. 이번 문서 승인만으로 재시도·큐·outbox를 도입하지 않는다.
- 담당 서비스·리포지토리·컨트롤러의 기존 테스트와 JaCoCo 기준값을 확인하고 테스트 페이지 지원 코드 및 확인한 경계·실패 사례 테스트를 추가한다.
- 전체 커버리지와 담당 코드 커버리지를 구분한다. 분모와 제외 대상을 기록하고, 보고서에서 제외된 코드를 검증했다고 주장하지 않는다.
- 커버리지 목표 비율은 기준 측정 후 근거와 함께 제안한다. 이번 단계에서 임의의 전체 프로젝트 기준을 강제하지 않는다.

## 7. 예상 변경과 검증

예상 변경은 로컬 페이지·서비스 워커·Firebase 웹 설정 예제, 로컬 지원 컨트롤러와 seed, 프로필·외부 연동 분리, Docker Compose, 필요한 계측·테스트·JaCoCo 설정, 실행 안내다. SES·S3 등 비대상 연동은 로컬 실행에 필요한 최소 대체만 제공하며 해당 기능의 테스트 화면은 만들지 않는다.

완료 기준:

1. 담당 기능과 커밋 근거, 화면/API 대응표 작성.
2. local-test 실행 및 기본 프로필에서 페이지·테스트 계정·토큰 지원 API 비노출 검증.
3. 상품·찜·키워드·담당 관리자 조회의 입력/응답 및 권한 경계 확인.
4. Firebase 웹 설정 절차와 포그라운드/백그라운드 수신 코드 제공, 실제 검증 여부 기록.
5. 쿼리 수 기준값과 N+1 재현 테스트, FCM 대기·오류 테스트, JaCoCo 결과 확보.
6. 관련 자동 테스트 실행 및 가능한 기존 회귀 검증. 환경 제약과 기존 실패를 구분하여 기록.
7. docs/result/로컬_기능_테스트_페이지.md에 변경 파일, 실행 방법, 측정 결과, 사용자 검증 항목과 후속 고도화 후보 작성.

## 9. 실제 성능 수치와 시각화 — 도구 채택 확정

사용자가 채택한 k6 + Prometheus + Grafana로 최적화 전후를 실제 측정값과 그래프로 보여주는 환경을 구성한다.

| 도구 | 역할 | 산출물 |
| --- | --- | --- |
| k6 | 일정한 시나리오로 부하 생성 및 클라이언트 관측 | p50/p95/p99 응답 시간, 초당 요청 수, 오류율, 웹 대시보드와 HTML 보고서 |
| Spring Boot Actuator + Micrometer | 애플리케이션 지표 노출과 사용자 정의 계측 | HTTP 처리, JVM 메모리·GC, DB 연결 풀, FCM 작업 지표 |
| Prometheus + Grafana | 서버 지표 수집·저장·시각화 | 시간에 따른 API/JVM/DB 풀/FCM 대시보드 |
| datasource-proxy | JDBC 실행 계측 | 격리된 시나리오별 SQL 횟수와 실행 시간, N+1 회귀 검증 |
| JaCoCo | 자동 테스트 실행 범위 확인 | 담당 코드 라인·브랜치 커버리지 HTML 보고서 |

k6는 부하를 만들고 Grafana는 서버에서 수집한 지표를 보여준다. k6 자체 웹 대시보드와 HTML 보고서를 함께 사용하므로 k6 데이터를 Grafana에 직접 전송하는 연동은 초기 필수 범위로 삼지 않는다. 커버리지는 성능 지표와 구분하여 표시한다. JMeter는 이번 구현 범위에서 제외한다.

Grafana 패널 제안:

- 조회 API: 요청률, 오류율, 응답 시간 분포. 서버 p95/p99를 표시할 경우 Micrometer histogram bucket을 설정하며 k6의 클라이언트 관측값과 구분한다.
- 자원: JVM 메모리·GC 시간, 프로세스 CPU, DB 활성/대기 연결 수.
- N+1 비교: 동일 페이지 크기별 SQL 실행 횟수 및 조회 시간. 격리 테스트의 측정 결과를 비교 보고서로 남기며 전역 SQL 통계 차이를 동시 요청별 수치로 표시하지 않는다.
- FCM: 작업 제출·성공·실패 수, 큐 대기 시간, 전송 처리 시간, 활성 작업 수와 거절 수. 실제 executor 도입 전에는 존재하지 않는 지표를 0으로 꾸미지 않고 미적용으로 표시한다.

측정 규칙:

1. 개선 전·후 커밋, 데이터 seed와 규모, 페이지 크기, JVM/DB 설정, 자원 제한, 부하 조건, 워밍업·측정 시간을 저장한다.
2. 초기 부하는 낮게 시작하고 동일한 단계별 조건으로 반복한다. 고정 도착률 시나리오에서는 목표 요청률과 실제 달성 요청률, dropped iterations도 함께 기록한다.
3. 동일 로컬 장비에 DB·서버·부하 도구·모니터링이 함께 실행되는 자원 경쟁을 명시한다. 측정값을 운영 환경의 최대 처리량으로 일반화하지 않는다.
4. JaCoCo 실행과 부하 성능 측정은 분리한다. SQL 계측·로깅·모니터링 조건은 전후 동일하게 맞춘다.
5. FCM 반복 부하는 제어 가능한 전송 대역을 사용하고 지연 조건을 기록한다. 실제 Firebase 수신은 소수의 기능 검증으로 분리하고 모의 전송 처리량을 Firebase 처리량으로 표현하지 않는다.
6. 비동기 개선은 API 응답뿐 아니라 작업 완료량, 실패율, 큐 누적, 완료까지 걸린 시간으로 판단한다. 테스트 종료 후 남은 작업도 확인한다.
7. 실제 실행 전에는 결과를 '미측정'으로 표시한다. 전후 원본 보고서, 측정 조건, 그래프와 개선율 계산 근거를 docs/result에 연결한다.

추가 파일은 k6 시나리오, Prometheus 설정, Grafana 대시보드 및 provisioning, Compose 모니터링 서비스, Micrometer/SQL 계측 설정이다. 모니터링 엔드포인트는 로컬 환경으로 제한한다. 현재 단계에서는 계획만 보완하며 설치나 구현은 시작하지 않는다.

## 10. Docker 로컬 실행 구성

### 서비스와 파일

Dockerfile은 백엔드/데이터 생성기의 이미지를 빌드하는 용도로, Compose 파일은 여러 서비스를 연결하고 실행하는 용도로 사용한다. MariaDB·Redis·Prometheus·Grafana·k6는 공식 이미지를 사용하며 호환성을 확인한 버전으로 고정한다. Kubernetes와 Grafana Cloud는 사용하지 않는다.

| 서비스 | 구성 및 역할 |
| --- | --- |
| mariadb | 테스트 전용 DB, UTF-8 문자 설정, 영속 볼륨, readiness healthcheck |
| redis | 테스트 전용 Redis, healthcheck, 테스트 환경에 맞춘 영속성 설정 명시 |
| app | Java 17 백엔드 이미지, local-test 프로필, DB/Redis 정상 준비 후 기동 |
| seed | 명시적으로 실행하는 일회성 대용량 데이터 생성 작업, 완료 후 종료 |
| prometheus | app의 Actuator 메트릭 수집, 수집 주기·보존 기간 설정과 볼륨 |
| grafana | 데이터 소스와 대시보드 자동 provisioning, 볼륨 |
| k6 | 명시적으로 실행하는 일회성 부하 테스트, 호스트에 결과 파일 저장 |

예상 파일:

- `compose.local-test.yml`: 공통 서비스, 네트워크, 볼륨, healthcheck, 자원 제한.
- `docker/local-test/Dockerfile`: 로컬 측정용 백엔드/seed 실행 이미지. 기존 배포 Dockerfile과 구분한다.
- `docker/local-test/.env.example`: 포트, DB 계정, JVM/컨테이너 자원, 데이터 규모 등 설정 예제.
- `docker/local-test/prometheus/`, `docker/local-test/grafana/`: 수집 설정과 자동 대시보드 구성.
- `scripts/local-test/`: PowerShell 실행·seed·검증·측정·대상 한정 초기화 스크립트.
- `performance/k6/`: 시나리오와 데이터 프로필, 실행 가이드.
- `artifacts/performance/<run-id>/`: 원본 측정값, HTML, seed manifest, 실행 조건. 대형 산출물은 Git에서 제외한다.

현재 `.gitignore`가 모든 JSON/CSV를 제외하므로 Grafana 대시보드 등 필요한 설정 파일만 좁게 예외 처리한다. 서비스 계정 JSON, 개인 환경변수, 대용량 더미 데이터와 원본 결과는 제외 상태를 유지한다.

### 실행 모드 및 연결

- 기본 측정 모드: 백엔드까지 Compose에서 실행해 JVM/CPU/메모리 설정을 고정한다.
- 개발 모드: MariaDB·Redis·모니터링은 Docker, 백엔드는 IntelliJ에서 실행한다. 모드별 결과를 직접 혼합하지 않는다.
- 컨테이너 간 연결은 `mariadb`, `redis`, `app` 등 서비스 이름을 사용한다. IntelliJ 모드의 Prometheus/k6 대상은 Docker Desktop의 호스트 연결 주소를 사용하도록 별도 설정한다.
- 컨테이너 안의 app은 컨테이너 네트워크에서 접근 가능하게 바인딩하고, 호스트로 공개하는 포트는 127.0.0.1로 제한한다. 앞 절의 루프백 정책은 호스트 공개 범위를 의미한다.
- 시작 순서는 healthcheck 기반으로 구성한다. seed는 스키마 준비 이후, k6는 seed 완료·정합성 확인 이후에만 시작한다.
- DB/Redis 데이터는 일반 중지·재시작 시 유지한다. seed 및 초기화는 서버 시작마다 자동 실행하지 않는다.
- 초기화 스크립트는 이 Compose 프로젝트의 테스트 DB와 Redis 키만 대상으로 삼는다. 전체 Docker prune이나 다른 프로젝트 볼륨 삭제는 사용하지 않는다.
- 실제 Firebase 자격증명은 필요할 때만 읽기 전용 마운트하고, 모의 모드에는 요구하지 않는다.

계획 확인 시 Docker CLI 29.7.2, Compose v5.4.0이 확인됐다. 현재 도구 권한에서 Docker 설정 파일 및 엔진 접근이 거부되어 엔진 정상 작동과 컨테이너 실행은 아직 검증하지 못했다. 구현 시 Docker Desktop의 Linux 컨테이너 모드, 사용 가능 CPU/RAM/디스크, 포트 충돌과 엔진 접근을 먼저 확인한다.

## 11. 대용량 더미 데이터 생성

### 데이터 규모

아래 수치는 생성 목표이며 현재 적재되거나 측정된 결과가 아니다. 파라미터로 조절 가능하게 제공한다.

| 프로필 | 사용자 | 상품 | 찜 관계 | 키워드 | 용도 |
| --- | ---: | ---: | ---: | ---: | --- |
| smoke | 100 | 1,000 | 5,000 | 200 | 실행과 데이터 정합성 확인 |
| small | 1,000 | 10,000 | 50,000 | 2,000 | 기본 부하와 N+1 재현 |
| medium | 10,000 | 100,000 | 500,000 | 20,000 | 주 비교 기준 |
| large | 100,000 | 1,000,000 | 5,000,000 | 200,000 | 대용량 선택 실행 |

기본 실행은 smoke, 대표 성능 측정은 medium을 목표로 한다. large는 자원 확인 후 별도 명령으로 실행한다. 장비 부족으로 낮은 규모만 실행한 경우 실제 적재 규모와 미실행 단계를 결과에 명시한다.

### 분포와 정합성

- 난수 seed와 생성 기준 시각을 고정하고 학교·판매자·카테고리·가격·상태·생성일을 분산한다.
- 균등 분포와 인기 상품에 찜이 몰리는 편중 분포를 별도 프로필로 제공한다. 특정 사용자에게 많은 찜이 있는 목록도 구성한다.
- 없는 검색어, 소수 일치, 다수 일치, 가격 경계, 정렬 값 동률, 삭제 상품, 깊은 페이지를 확인할 데이터를 만든다.
- 키워드는 미일치·일반 일치·다수 사용자 일치 그룹으로 구성한다. 전체 키워드 수와 실제 매칭 수신자 수를 분리한다.
- 동일 사용자/상품의 찜 중복과 외래키 누락이 없게 생성한다. 생성 후 실제 테이블 건수·중복·참조 무결성·분포를 검증한다.
- 가상 사용자와 이미지 경로만 사용하고 S3 업로드나 실제 이메일 발송을 하지 않는다.
- 채팅 API는 제외한다. 상품 쿼리의 채팅 수 조인에 필요한 관계 데이터만 제한된 fixture로 생성할 수 있으며, 생성 건수와 집계 기대값을 manifest에 기록한다. 채팅 기능 테스트로 확장하지 않는다.
- 더미 FCM 토큰은 모의 전송 전용으로 분리하고 실제 Firebase 대상으로 사용하지 않는다.

### 적재 방식

- 로컬 전용 seed 명령에서 JDBC prepared statement의 청크/배치 적재를 사용한다. 현재 엔티티의 IDENTITY 전략을 고려해 JPA saveAll만으로 대량 배치가 된다고 가정하지 않는다.
- 청크 크기는 초기 1,000건을 기준으로 설정 가능하게 하고 청크별 커밋·진행률·오류 건수를 기록한다. 수백만 건 전체를 메모리나 단일 트랜잭션에 담지 않는다.
- 외래키 순서를 지키고 필요한 기본값·감사 시각을 명시한다. 적재 속도를 위해 무결성 검증을 생략하지 않는다.
- API/서비스를 우회한 데이터 준비이므로 상품 등록 로직이나 FCM 처리 성능을 검증한 것으로 해석하지 않는다. 해당 성능은 별도 API 시나리오로 측정한다.
- manifest에 seed, 프로필, 분포, 목표/실제 건수, 생성 시각, 스키마/코드 버전, 적재 시간, DB 크기를 저장한다.
- 같은 manifest의 완료 데이터가 있으면 중복 적재를 거부하거나 건너뛴다. 중단된 적재는 불완전 상태로 표시하고 대상 한정 초기화 후 재생성하는 절차를 제공한다.
- 읽기 전용 조회 측정은 동일 데이터를 재사용한다. 상품 생성/FCM 측정은 반복마다 동일 초기 상태로 복구하고 쓰기 때문에 증가한 데이터 수를 기록한다.

## 12. 부하 시나리오와 전후 비교

### 시나리오 구분

| 시나리오 | 고정/변경 조건 | 측정 내용 |
| --- | --- | --- |
| 상품 조회 | 필터 선택도·정렬·첫/깊은 페이지, 동일 DB 규모 | p50/p95/p99, 요청률, 오류율, SQL 및 DB 상태 |
| 찜 목록 N+1 | 동일 데이터에서 페이지 크기 10·50·100, API 허용 범위 확인 | SQL 실행 수와 응답, 반환 결과 및 집계 정확성 |
| 담당 관리자 조회 | 상품 상태·캠퍼스 필터 | 조회 지연·처리량과 결과 정합성 |
| 키워드 FCM | 실제 매칭 수신자 1·10·100명, mock 지연 0·50·200ms | API 응답, 전송 완료·실패, 잔여 작업과 완료 지연 |
| 장시간 유지 | 대표 규모·안정 부하 | 메모리·GC·DB 풀·시간 경과에 따른 지연 |

FCM 조건은 모두 한 번에 조합하지 않고 작은 fan-out/지연부터 단계적으로 실행한다. mock 지연은 비교 실험의 통제값이며 Firebase의 실제 지연 분포라고 주장하지 않는다. 실제 Firebase 웹 수신은 기존 소수 기능 검증으로 유지한다.

### 부하 단계

- 준비: 데이터 검증 → app 준비 확인 → 테스트용 JWT/유효 ID 생성 → 단일 요청으로 응답 본문 검증.
- 워밍업: 초기 기준 1분. 본 측정에는 포함하지 않는다.
- 측정: 한 iteration당 API 한 번 호출하는 조회 시나리오에서 10 → 30 → 100 요청/초를 출발점으로 사용한다. 각 단계는 초기 기준 3분, 동일 조건 3회 반복한다.
- 위 부하는 목표 입력값이며 달성 가능한 성능을 의미하지 않는다. 장비·API별 smoke 결과를 보고 조정하고, 결정된 조건은 전후 동일하게 유지한다.
- 고정 도착률에서는 목표/실제 요청률, VU 한도, dropped iterations를 기록한다. 요청을 시작하지 못한 이유와 서버 오류를 구분한다.
- 오류·타임아웃 급증 또는 메모리/대기 작업 한도 초과 시 시나리오를 중지하도록 설정한다. 중지·누락도 결과에 남기고 성공한 요청만으로 성능을 요약하지 않는다.
- N+1 SQL 수 검증은 부하 테스트와 별개로 격리 실행한다. latency 측정 시 상세 SQL 본문 출력은 끄고 계측 조건을 고정한다.
- 캐시가 예열된 결과와 재시작 직후 결과를 구분한다. 일반적인 재시작만으로 OS/DB의 모든 캐시가 비워졌다고 가정하지 않는다.

### 시각화 및 산출물

- k6 HTML: 시나리오별 지연 분포·처리량·오류와 목표 부하 미달 여부.
- Grafana: 같은 시간 범위의 API 지연·요청률·CPU·메모리·GC·DB 풀·FCM 관측 지표.
- 비교 표: 데이터 규모, 페이지 크기, SQL 수, p95/p99, 실제 처리량, 오류율, 측정 조건과 전후 커밋.
- 각 반복의 지표를 보존한다. 반복별 p95를 단순 평균해 전체 요청의 p95로 표시하지 않는다.
- 개선 전 baseline은 이번 작업에서 확보한다. 개선 후 수치는 후속 최적화 승인·구현 이후 동일 시나리오로 확보한다. 현재 단계에서 가상의 개선율을 채워 넣지 않는다.

## 13. 보완된 작업 순서와 승인 범위

1. Docker 엔진·자원 확인 및 Compose 설정/백엔드 이미지 작성.
2. local-test 프로필·테스트 사용자·외부 모의 연동·기능 페이지 구축.
3. seed generator 및 manifest/정합성 검사 구현, smoke 적재 검증.
4. Actuator/Micrometer·Prometheus·Grafana·SQL 계측과 자동 provisioning 구현.
5. small → medium 순서로 seed 및 부하 검증, 자원이 허용하면 large 실행.
6. Firebase 웹 실제 연동 코드와 사용자 설정 안내, 관련 자동 테스트/JaCoCo 검증.
7. 원본 성능 보고서와 재실행 명령, 실제 데이터 건수, 미검증 항목을 결과 문서에 기록.
8. 결과 문서 검토 후 사용자의 별도 허락을 받아 git add·commit·push.

도구 선정과 대용량/Docker 요구가 확정됐으며, 사용자가 2026-09-12에 구현 진행을 승인했다. 승인에 따라 1~7을 구현·검증한다. SQL/비동기 처리의 본격 최적화는 기존 합의대로 baseline 확보 후 별도 계획으로 진행한다.
