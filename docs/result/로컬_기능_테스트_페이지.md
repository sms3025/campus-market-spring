## 3. 실행 방법

`docs/local-test.md`에 전체 절차가 있다. 최소 실행은 다음과 같다.

```powershell
$env:JAVA_HOME='C:/Users/SSAFY/.jdks/ms-17.0.20.1'
$env:GRADLE_USER_HOME="$PWD/.gradle-local"
./scripts/local-test/run.ps1 -Action Build
./scripts/local-test/run.ps1 -Action Seed -Scale medium
./scripts/local-test/run.ps1 -Action Start
node scripts/local-test/verify-api.mjs
./scripts/local-test/baseline-suite.ps1 -Part Likes
```

테스트 페이지 http://localhost:8080/local-test/, Grafana http://localhost:3000/d/campus-local, Prometheus http://localhost:9090/targets 를 사용한다. 호스트 공개 포트는 모두 127.0.0.1로 제한했다.

### 4.5 개선 전 baseline 측정

모든 부하는 k6 고정 도착률이며 iteration 1회당 API 1회를 호출한다. 워밍업 1분은 측정에서 제외하고 본 측정 3분을 사용한다. 지연은 k6 클라이언트 관측값(ms)이고 SQL 수는 응답 헤더에서 수집한 요청 스레드 JDBC 실행 수다. 반복별 값을 그대로 싣고 평균하지 않는다.

| 3 | 10 | 13 | 3.4 ms | 8.7 | 8.4 | 10.5 | 12.2 | 14.4 | 10.00 | 0% |

각 실행은 1,800회 요청이며 dropped iterations는 모두 0이다. 페이지 크기가 10배가 되면 SQL 실행 수는 13→103건, 요청당 SQL 시간은 약 3.4ms→15.1ms, p50은 약 8.4ms→25.6ms로 증가한다. 첫 반복의 값이 이후 반복보다 높은 것은 재시작 직후 캐시가 예열되지 않은 상태이기 때문이며, 반복 2·3이 예열 후 값이다.

이 수치는 10 req/s의 낮은 부하에서 얻은 값이다. 절대 지연이 아직 작다는 점보다, 반환 항목 수에 비례해 쿼리 수와 DB 시간이 함께 늘어난다는 구조가 이 측정의 결론이다.

### 4.6 개선 작업

baseline에서 확인한 세 가지를 고쳤다. 각 항목은 독립적으로 적용했고, 측정은 셋을 모두 반영한 이미지에서 수행했다.

| # | 대상 | 변경 |
| --- | --- | --- |
| P1 | `LikeRepositoryImpl.findAllByUserId` | 채팅방·찜을 함께 조인하고 `group by like.likeId`로 묶던 구조를 상품 기준 상관 서브쿼리 집계로 교체. 결과를 순회하며 항목마다 찜 수를 다시 조회하던 루프 제거 |
| P2 | `KeywordRepository`, `KeywordService` | 조건 없는 전체 조회 + 자바 스트림 필터를 `findMatchingKeywords` 쿼리로 이동. 캠퍼스·작성자·제목 조건을 SQL에서 처리하고, collation 차이로 결과가 넓어지지 않도록 대소문자 일치 검사만 애플리케이션에 남김 |
| P3 | `ItemService`, `KeywordNotificationListener`, `FcmService`, `FcmNotificationService`, `AsyncConfig` | 등록 트랜잭션 안에서 수신자마다 `sendAsync().get()`으로 대기하던 전송을, 커밋 이후 전용 executor에서 실행하도록 변경. 토큰 조회를 `in` 절 1회로, 전송을 `sendEach` 배치 1회로 통합 |

P1에서 루프가 존재했던 이유는 단순 실수가 아니었다. 메인 쿼리가 `group by like.likeId` 상태에서 채팅방을 조인하고 있어 그 자리의 `like.count()`가 상품의 찜 수가 아니었고, 그 값을 보정하려고 항목별 재조회가 붙어 있었다. 따라서 수정 방향은 쿼리 수를 줄이는 것이 아니라 집계를 한 번에 올바르게 구하는 것이었다.

P2에서 애플리케이션 필터를 완전히 없애지 않은 이유는 동작 보존이다. MariaDB 기본 collation(`utf8mb4_unicode_ci`)의 `locate`는 대소문자를 구분하지 않는 반면 기존 자바 `String.contains`는 구분한다. DB 결과가 기존 조건의 상위 집합이므로, 좁혀진 후보에 기존 조건을 한 번 더 적용해 알림 대상 집합을 동일하게 유지했다.

P3에서 재시도·큐 영속화(outbox)는 넣지 않았다. 중복 알림 방지 설계가 함께 필요하고, 현재 단계에서는 실패·거절·잔여 작업을 관측할 수 있게 만드는 것까지를 범위로 정했다.

구현은 완료했고 실제 수신은 사용자 실행 항목으로 남긴다.

- 제공: 웹 설정·VAPID 입력 화면, 알림 권한 요청, 서비스 워커 등록(scope `/local-test/`), 토큰 발급과 테스트 계정 연결, 포그라운드 수신 로그, 백그라운드 메시지 전달, 같은 origin으로만 이동하는 알림 클릭 처리.
- 서버: `FCM_REAL=true`일 때만 Admin SDK를 초기화하고 `/run/secrets/firebase.json`을 읽기 전용으로 읽는다. `mock-` 접두사 seed 토큰은 실제 전송에서 건너뛴다.
- 미검증: 실제 Firebase 프로젝트 자격증명이 필요한 브라우저 수신(포그라운드·백그라운드 알림, deeplink 클릭 이동). 자격증명이 없으므로 성공으로 기록하지 않는다.
- 검증한 부분: 모의 모드에서 키워드 일치 시 전송 대상 선정, 본인 상품 제외, 전송 완료·실패 기록, 토큰 등록 API.

## 5. 남은 한계와 사용자 검증 항목

1. Firebase 웹 실제 수신은 사용자 자격증명이 필요하다. 콘솔에서 테스트 프로젝트·웹 앱·VAPID 키를 만들고 서비스 계정 JSON을 `docker/local-test/secrets/firebase.json`에 배치한 뒤, `FCM_REAL=true`로 기동해 포그라운드·백그라운드 수신과 알림 클릭 이동을 확인한다. `docs/local-test.md` 6절 절차를 따른다.
2. `large` 프로필(상품 100만·찜 500만)은 적재하지 않았다. 자원이 허용되면 같은 시나리오를 반복한다.
3. 깊은 페이지 비용은 측정하지 않았다. 모든 부하는 첫 페이지 기준이다.
4. 모든 수치는 단일 로컬 장비에서 DB·앱·부하 도구·모니터링이 함께 동작하는 조건의 값이다. 운영 환경의 처리량으로 일반화하지 않는다.
5. 결과 문서를 검토한 뒤 git add·commit·push 허락 여부를 결정한다.

## 6. 다음 단계

상세 계획은 [후속 성능 고도화 계획](../plan/후속_성능_고도화_계획.md)에 있다. 이번 측정으로 확인한 우선순위는 다음과 같다.

1. **상품 검색·관리자 목록의 집계 조인 정리.** 이번에 고친 찜 목록과 동일한 구조가 남아 있고, 측정에서 가장 큰 병목이다. 관리자 목록은 단건 0.5초, 10 req/s에서 실제 처리량 0.8 req/s다.
2. **인덱스 검증.** `item(campus_id, is_deleted, created_date, item_id)`, `likes(item_id)`, `chat_room(item_id)` 후보를 실행 계획으로 확인한다. 조회와 등록을 함께 측정해 쓰기 비용 증가를 본다.
3. **깊은 페이지 비용 측정** 후 필요 시 no-offset 페이지네이션 검토.
4. **알림 재시도·outbox**는 전송 실패·거절 지표가 0이 아닐 때 착수한다. 현재는 0이다.
5. **커버리지 목표**는 담당 범위 baseline을 기준으로 `ItemService` 등 낮은 구간부터 제안한다.
